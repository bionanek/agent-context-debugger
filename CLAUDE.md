# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

A single-purpose tool that parses a real Claude Code transcript (`.jsonl` under `~/.claude/projects/<encoded-cwd>/`) plus the relevant `CLAUDE.md` and skill files, and emits **one self-contained HTML file** with all the data baked in. The HTML is the product — there is no server, no build system, no package manager. The output is meant to be opened in a browser and used as an investigative IDE for "what context did the agent actually use on this turn?".

There are two HTML artifacts in the repo:
- `agent-context-ide-prototype.html` — hand-written static mockup. Reference for layout/styling only; not generated.
- `agent-context-ide-real.html` — the script's output, regenerated by running the script. Treat as a build artifact.

Per-turn scoping is the core design: a turn spans one real user prompt to the next, and every verdict, cost and rollup is computed per turn as well as session-wide. The Blocks view navigates by drilling (see Architecture below).

## Running

```bash
# Generate the HTML for the most recent session in this cwd
python3 build_real_view.py

# List all sessions discoverable for this cwd
python3 build_real_view.py --list

# Pick a specific session by id prefix
python3 build_real_view.py --session abc12345

# Single-session output (skip the multi-session picker)
python3 build_real_view.py --no-all-sessions

# Compare two baked sessions (id prefixes) — adds the Compare tab.
# Off by default: without it, no compare payload is baked at all.
python3 build_real_view.py --compare abc12345 def67890
```

### Query mode (read-only, no HTML)

`--query` answers in plain text instead of building the page, reading the same
baked JSON the page renders. It writes nothing and never opens a browser. Each
listing prints the ids the next query needs, so three commands take you from
zero knowledge to one block's verdict:

```bash
# 1. every session: id, when, turns, tokens, prompt preview
python3 build_real_view.py --query sessions

# 2. what happened, and what was in context
python3 build_real_view.py --query abc12345 turns
python3 build_real_view.py --query abc12345 blocks
python3 build_real_view.py --query abc12345 turn-2 blocks

# 2b. the same drill-down the page offers: the scope's context files, active
# ones first, each with the summary line the File level shows, then one file
python3 build_real_view.py --query abc12345 turn-2 files
python3 build_real_view.py --query abc12345 turn2-users-jakuburban-claude-claude-md

# 2c. the subagent runs the session spawned, then one of them
python3 build_real_view.py --query abc12345 agents
python3 build_real_view.py --query abc12345 turn-2 agents
python3 build_real_view.py --query abc12345 agent-toolu_017xzfvjAFYgsyjCxkr3zzQQ

# 3. one block's verdict, reason and moments (block ids come from step 2)
python3 build_real_view.py --query abc12345 users-jakuburban-claude-claude-md-0-how-to-talk-to-me

# Bounds: fields cap at ~1500 chars and listings at 60 rows. Anything elided
# prints the exact command that returns the rest:
python3 build_real_view.py --query abc12345 <block-id> --field content
python3 build_real_view.py --query abc12345 blocks --all
```

A block's output includes its `rule` line - the rule-check state, its findings with file, line and matched text, and the reason a rule could not be checked - and a `[todo]` line naming `/compile-rules` when the rule has no reviewed record behind it.

A session's output includes the `rules` / `todo` lines: how many of the project's rules are compiled, reviewed as not checkable, uncompiled or stale, one line per rule document, and the one command that closes the gap. `--query sessions` repeats the hint, because the listing is a fresh reader's first command.

A file's output includes its active/quiet group, its `rollup.summary`, how often
the session read or edited it, its attributed cost, and its block list.

An agent's output includes its lane, the turn it was spawned in, its runtime,
tokens and tool calls, every report-back it sent, the on-disk subagent
transcript it names (which this tool deliberately does not read), and the two
fields no other view shows: the `brief` the main agent wrote and the `result`
that came back. `--field prompt` / `--field result` print either in full. The
`agents` listing is in spawn order and names each agent's lane and the fan-out
it was collapsed into, all read straight off the baked `agents` / `turnRows`,
so the CLI and the page describe one picture.

An address is `sessions` | `<session-id-prefix> [turn-N] [turns|files|blocks|agents|<file-id>|<block-id>|agent-<id>]`.
A leaf token is resolved as a block id first and a file id second, so every id
that resolved before the `files` level existed still resolves to the same block.
An `agent-` token addresses a subagent run, but still falls through to the block
and file lookups first: a file really can be called `agent-foo.md`, and its slug
must stay reachable.
An unknown id exits non-zero with the commands that list the valid ones.

There is no linter config and no dependency beyond the Python 3 standard library.

## Tests

```bash
# Run the whole suite (bare `pytest` - `python3 -m pytest` won't find it,
# pytest is not installed for the default python3 on this machine)
pytest
```

`tests/` holds a pytest suite. `tests/conftest.py` puts the repo root on `sys.path`, so tests `import build_real_view as brv` directly.

The convention is in-memory event builders, not jsonl fixtures on disk: `tests/test_turns.py` defines `user_text`, `user_slash`, `user_tool_result`, `assistant_text`, `assistant_tool_use` and `_ts`, and other test modules import them. Assemble a small event list, run it through a pipeline function, and assert on the returned dict/JSON structure. Never assert on HTML strings: the template is not a stable contract.

New areas go in `tests/test_<area>.py` in the same style. Verifying a change means `pytest` green *and* regenerating the HTML and opening it.

`tests/test_regression_verdicts.py` is the verdict regression harness and is not a normal test module: it encodes the verdicts a hand audit of real sessions proved wrong (the anchors and failure mechanisms are §7 and §2 of `docs/judgement-reliability-research.md`), one case per finding, tagged by mechanism in the test name (`pytest -k f_pathtable`). Cases whose fix has not landed yet are `xfail(strict=True)`, so a fix must flip its own cases to passes and delete the marker; leaving the marker on a case that now passes fails the suite deliberately. The `test_counter_anchor_*` cases are the verdicts the audit found *correct* - a change that flips one of those has made the judging worse, not better.

## Architecture

`build_real_view.py` is a single ~8k-line script structured as a linear pipeline. The numbered comment banners inside the file (`# ---------- 1. parse CLAUDE.md ----------` etc.) are the canonical section map — follow them when navigating. Two small stdlib-only modules sit beside it: `ctxlog_facts.py` (reads the hook log at `~/.claude/ctxlog/<session>.jsonl`) and `rule_checks.py` (compiled rule checking, see below).

Pipeline, in order:

1. **Discovery** (`discover_all_transcripts`, `encode_cwd_for_projects`) — Claude Code stores transcripts at `~/.claude/projects/<encoded-cwd>/*.jsonl`, where the encoding replaces both `/` and `.` with `-` (so `/Users/x/famigo/.claude/worktrees` becomes `-Users-x-famigo--claude-worktrees`). Only top-level `*.jsonl` files are transcripts; sub-agent runs live in per-session subdirectories and are excluded by not recursing. There is no `isSidechain` check — the old first-line probe never matched anything.
2. **CLAUDE.md parsing** (`parse_claude_md`, `classify_block`) — splits each `CLAUDE.md` into H1/H2 blocks, ignoring headings inside fenced code. Each block gets a `kind` (rule, skill-pointer, reference, etc.).
3. **Transcript parsing** (`load_transcript`, `tool_calls`, `assistant_text_segments`, `first_real_user_prompt`). One classifier, `_real_user_prompt_text`, decides what counts as a real user prompt, and both turn splitting and first-prompt extraction go through it so they can never disagree. It flattens list-shaped `message.content` (the shape a pasted screenshot makes: an `image` item plus a `text` item) by joining the `text` items, and rejects tool-result lists, meta events, interrupt markers, `<local-command-stdout>` wrappers, `<command-name>` wrappers for local commands (`/model`, `/config`, recognised by the stdout wrapper that follows them), and `<task-notification>` wrappers. Skill and slash-command wrappers still count.

   **A task-notification is never a turn.** It arrives on the user channel but it is the *result half* of an `Agent` / `Task` / `Workflow` tool call, not something a human typed. Counting one inflated turn counts (48 turns became 24 on one real session) and stole the tool calls that followed it from the turn that earned them. The tag check lives in `_real_user_prompt_text` beside the caveat and interrupt rejections, and both it and `_task_notification_text` `lstrip()` first so the two classifiers can never disagree about the same event.
3b. **Subagent runs** (`agent_runs`, `parse_task_notification`, `attach_subagent_transcripts`, script section `2a`) - pairs every spawn to its report-back by tool-use id and decides everything the views draw. Returns `agents`, the ordered `turnRows`, and a count of `unmatchedNotifications`.

    The notification is generated text, so every tag is parsed with an explicit regex and a missing one is *unknown*, never an error: real sessions carry notifications with no `<tool-use-id>` at all, and one raise there would lose every agent in the session. **One spawn can notify more than once** (an agent notifies each time it stops with no live children and can be resumed), so a second notification appends to the same agent's `returns[]` rather than inventing a second agent. A notification naming a tool call that is not a spawn (a background `Bash`) is neither an agent nor unmatched; only one that ties to nothing at all is counted, and `main` prints a warning rather than swallowing it, because a lost pairing silently reports a finished agent as never returning.

    **Lane and colour are baked, not derived in the browser.** An agent takes the lowest free lane on spawn and releases it on its *last* return, so an agent that never reports keeps its lane to the end of the session, which is what makes its unfinished track visible. Colour is `AGENT_PALETTE[colorIndex % 6]` in spawn order and means **identity, never direction**: with five agents in flight one hue makes the tracks impossible to tell apart, so direction is carried only by the icon and the badge. Computing any of this in JavaScript would let `--query` and the page describe the same session differently.

    **A fan-out collapses only when every member returned before the next turn row**, never merely because it was spawned together (`_collapse_fanouts`). Keying on "spawned together" would bury the single case most worth seeing: the agent that did not come back.

    **The subagent's own transcript is deliberately not loaded.** The harness writes it to `<session>/subagents/agent-<task-id>.jsonl`; its tool calls carry whole file contents and the report is already tens of megabytes. `attach_subagent_transcripts` resolves the path in Python and bakes it on each return record, so the agent screen and `--query` name the same file, and both say plainly that it is not baked in rather than implying completeness. A consequence worth stating: nested agents (an agent spawning its own children) live in that file, so every count here is main-thread spawns only.

    Agent payload: each record in `perSession[id].agents` carries `id` (the spawn's tool-use id), `type`, `subagentType`, `name`, `prompt`, `promptPreview`, `spawnEventIdx`, `spawnTime`, `spawnTurnIndex`, `returns[]`, `status` (`returned` / `open`), `durationMs`, `tokens`, `toolUses`, `resultText`, `lane` and `colorIndex`. The last five come from the *latest* report only, which the agent screen says out loud for a multi-report agent. Each entry in `returns[]` carries `taskId`, `status`, `summary`, `resultText`, `tokens`, `toolUses`, `durationMs`, `eventIdx`, `time`, `turnIndex` and `transcriptPath`. `turnRows` is the ordered row sequence both the turns list and `--query` walk: `{kind: turn|spawn|return|spawn-group|return-group|dangling, ref|refs}`. Each turn payload gains `agentIds`, and `data.sessions[]` gains `agentCount`.

4. **Usage extraction** (`usage_series`, `usage_totals`, `cache_breaks`, `usage_for_turn`) - reads the `usage` object every assistant event carries, which is the only permitted source for headline token numbers (char-count estimates may appear only where explicitly labelled as estimates). One series entry per *API request*, not per assistant event: the harness writes one response as several events sharing a `message.id` and repeating the same usage verbatim, so the series dedupes on that id and each entry carries its event index, which is how `usage_for_turn` gives each turn its share without ever counting a request twice. `cache_breaks` flags the requests where the cached prefix was lost and repaid (cache read collapses against the previous request while cache creation spikes); those become `cache-break` timeline rows via the same insertion helper compaction rows use.
5. **Context-file loading** (`load_context_files`) — discovers every file the agent could plausibly have used: global `~/.claude/CLAUDE.md`, project `./CLAUDE.md`, skills under `~/.claude/skills/`, files the agent `Read`, files referenced via `@path` in CLAUDE.md, hook directive files, and pre-loaded attachments. Each is tagged with a `kind` and `scope` that drive grouping in the UI.

   Skills come from the harness's `skill_listing` attachment when present. Listing names keep their plugin prefix (`datadog:ddsetup`), and a prefixed name is resolved under the plugin cache (`~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/skills/<skill>/SKILL.md`, newest version wins) after the plain `~/.claude/skills` and project locations miss; a name that resolves nowhere becomes a listing-only entry carrying its description. Skill loading is **call-driven first, prompt-driven only as a fallback** (`_is_loaded`): a `Skill` tool call in the trace, then a slash-command wrapper the user typed, then a word-boundary `/name` mention in the prompt. The prompt match is bounded on both sides, so `/cpanel` does not load `cp` and a bare first word never loads anything.

   **The listing is a session fact, not a turn's** (`skill_listing`, passed down from `process_session`). The harness injects it once, so a later turn's event slice does not contain it - and a skill with no SKILL.md on disk exists *only* in the listing. Without the override such a skill appeared in the payload of the one turn carrying the attachment, normally turn 0 before it was invoked, and the per-turn combine then reported two skills that drove fifteen turns of a real session as `not-loaded`. Skills that resolve on disk are unaffected: the path-convention fallback finds them in every turn.
6. **Predicate extraction** (`derive_predicates`) — for each block, pulls checkable items out of it. Every predicate carries a `strength` of `strong` or `weak` (see step 8).

   **Only harness-defined signals are hardcoded here.** Everything this step reads is a record the Claude Code harness itself writes, identical for every user: a slash command being invoked, a `Skill` call, a file path a tool call carried, a bash command that ran. What a rule *says* is never pattern-matched, with one bounded exception (the slash command a trigger declaration names, below). That is the open-source line: two prose predicates used to be reverse-engineered from one user's own CLAUDE.md - `path-table` matched the literal table header "Project path contains", `end-of-message` matched one rule's phrasing and scored the closing paragraph against one author's writing style - and a third read five clipboard commands (`pbcopy`, `xclip`, `xsel`, `printf`, `echo`) out of bare prose because of one rule about them. All three are retired (§4 of `docs/judgement-reliability-research.md`): they judged one person's wording and would have judged the next user's rules, or another language's, as silence. A rule of that kind is now a compiled record in a checks file, which each user generates from their own rules via `/compile-rules` (step 8b) - a cwd-conditional obligation as `tool_never_without_prior` over the ordered tool log, a response-shape rule as a `communication`-scope record in the `judged` bucket. A rule nobody has compiled reports as uncompiled and names the command; it is never guessed at.

   The predicate kinds that remain are `trigger`, `skill-invocation`, `writes-to-named-path`, `template-echo`, `command-echo` and the weak `command-mention`. `tests/test_generalization.py::test_no_prose_derived_strong_predicate_survives_anywhere` holds that list against every rule document the suite carries, and a Polish fixture beside its English twin asserts the two derive the same predicates.

   The trigger predicate and the skill/command moments builder both ask `_trigger_evidence` - one matcher, bounded on both sides, over the three records of an invocation (a `Skill` call, a slash-command wrapper, `/name` in the prompt). While the predicate ran a bare substring test of its own, a prompt reading `/implement-plan-workflow` scored the `/implement-plan` pointer green with the moment card beside it saying, correctly, that the command was never invoked. There is deliberately **no negative ("never X") predicate**: it used to take the word after `never` and look for it among the session's bash commands, so a rule reading "never import another store's singleton" reported a violation because `import` appeared inside a ripgrep command. Prose negations are the job of step 8b.

   **A trigger declaration is recognised by its shape, not by an English word** (`_TRIGGER_DECL`). The declaration this tool reads is a short label, a colon, and the backticked slash command standing alone to the end of the line - so `Wyzwalacz: `/standup`` derives exactly what `Trigger: `/standup`` does. The two English cues (`Trigger:`, "types `/x`") are kept beside it because they also match declarations that run on into the sentence, but they are sugar: neither is required, and what they extract is a harness identifier rather than a claim about behaviour. The line has to *end* at the command, or "links to: `/deployment`, `/deployment/calibrate…`" - a real line in one audited AGENTS.md - becomes a predicate about a command that does not exist.

   **Trigger declarations are read, documentation examples are not** (`_example_spans`). A `Trigger:` line or a "types `/x`" phrase that sits *inside* an inline-code span or a quotation is prose about the syntax, so it derives nothing: this repo's own Architecture section otherwise produced live predicates printing "`/foo` not invoked this run" about a command that does not exist. A real declaration writes the phrase bare and backticks only the command, so it survives. A quote span may cross a newline and is length-bounded instead - a mispaired quote costs one predicate (`dormant`, an honest refusal), never a false accusation.

   **What the run did is evidence too** (`skill-invocation`, `writes-to-named-path`, `template-echo`, `command-echo`). The judging used to read the assistant's prose and its bash commands and nothing else, so a rule the agent demonstrably obeyed scored `unused` above a reason denying compliance. Four harness-defined joins close that: a `Skill` call or slash-command wrapper lifts that skill's own blocks (`derive_predicates` takes the file record for the name; a prompt that merely mentions `/name` is deliberately not enough, or every block of a skill goes green because the user typed its name); a backticked path the block names, joined to a path a tool call carried (`_path_names_target`); the block's own template literals found in a file the scope wrote (`_template_literals` / `_template_echo_hits`, reading `written_chunks` - Write/Edit content and heredoc bodies, because the memory-rule anchor appended with `cat >> $M/ERRORS.md <<'EOF'`); and a whole prescribed command that ran verbatim (`_command_echo_count`). All four are **credit-only**: `applicable` is the signal itself and `matches` is unconditionally true, so they lift a block and never accuse one - a session that never appended to ERRORS.md may have had nothing worth logging, and reading that silence as a violation is the mirror of the blind spot they exist to close.

   The path join resolves both sides and then falls back to a contiguous run of path components in **either** direction, because either side can be the partial one: the block's side is often relative (`docs/decisions/DECISIONS.md`, which would resolve against this process's cwd), and a shell-written path is routinely `$M/ERRORS.md`, whose unresolvable segments `_path_components` drops. Command echo reads **every** fence, not only shell-tagged ones - the tag requirement exists to stop `import re` being read as a program, and a candidate that must then have run verbatim cannot make that mistake, which is what the palletizer `AGENTS.md` anchor needs with its `just` recipes in a bare fence.

   **Command-mention extraction is shape-first, and fences are read separately.** Inline spans go through `_looks_like_command_word`: lower-case, `-` rather than `_`, no trailing separator, at least four characters, and not in `NON_CMDS` (English prose, the nouns every technical document uses for a field or a value, common data-format names, shell keywords). Markdown table rows are excluded first (`_strip_table_rows`): a cell is data, and one column of the retired gh-account table held the repo names `figma` and `formic`, both harvested as programs, so every bash line naming the repo looked like a hit on a rule about GitHub accounts. `_named_paths` still reads tables, because a rule really can put the file it governs in one. `NON_CMDS` no longer carries the entries that were only ever this tool's own vocabulary (`argparse`, `claude.md`, its verdict statuses) - a list curated against one repo's documents grows by an entry per false positive and says nothing about the next user's rules. It is still English, knowingly: deriving stopwords from the user's own corpus belongs to the lexical tier, and this tier can only ever reach `possibly-referenced`, so a leftover false positive claims the block was referenced and can never accuse it. A wordlist alone cannot keep up with a dense technical document - the Architecture block put 167 inline spans through here, nearly all identifiers - and the four-character floor costs the weak tier `gh`, `git` and `jq`, which is the right trade: a command mention can never reach a hard verdict, so all a short false positive can do is claim the block was referenced when nothing tied it to the run. Shell-fenced blocks are read by `_fenced_commands`, which keeps the **whole** command (`yarn type-check`, split on `&&`/`|`/`;`, with an inline `# comment` stripped) and applies neither filter to the first word, because a fence line's first word is a command by position. Before this the fence body was scanned as one inline span, so its language tag `bash` became "the command the rule is about" while the famigo quality gate's 21 real `yarn type-check` runs stayed invisible. For the weak tier only an explicitly shell-tagged fence counts (`_extract_fenced_commands`), and only its single-word commands: a multi-token command belongs to `command-echo` above, so the same command never occupies two evidence rows at two strengths.
7. **Moment assembly** (`assemble_moments` and the family of `_moments_for_*` functions) — given a block and the trace, constructs the chronological "How the agent ended up here" cards (TRIGGER → INTENT → ACTION → OUTCOME). Each predicate type has its own moment-builder, the structural kinds included (`_moments_for_structural`): a block lifted by a write or a verbatim command run otherwise fell through to the loose-keyword cards, putting a topical-overlap narrative under a badge earned by something else entirely.

    **A card is a causal claim, so the causal kinds are gated on the evidence tier.** TRIGGER → INTENT → ACTION reads as "the block caused this", and lexical overlap cannot support it: a Figma design-system block narrated itself with a rate-limiting review because both contain "design", and a tech-stack table with an Effect-vs-react-query discussion because both contain "React". Two non-causal kinds carry that weight instead, each disclaiming causation *in its own card text* (`CO_OCCURRENCE_NOTE` / `THINKING_SELF_REPORT_NOTE`) rather than trusting the reader to know which kinds are weak. `co-occurrence` is what a block gets when the only evidence is shared wording — `_moments_for_loose_keyword` returns exactly one such card and `assemble_moments` returns it untouched, because a second card there starts reassembling the narrative — and it is also what a bare command mention gets (`_moments_for_command_mention`), still citing the run count and the command verbatim, and what a bare `/name` in the prompt gets in `_moments_for_skill_or_command`, since `skill-invocation` refuses a mention as evidence the skill ran and a ✓ TRIGGER there put a green step above the weaker badge that refusal earns. `corroboration` is readable extended thinking, below.

    **The card and the badge read one overlap** (`_keyword_overlap`): `assess_block` tokenized the block one way for the `unused` / `possibly-referenced` split and the card builder another, so a block could sit `unused` — "no keyword overlap with the assistant's reasoning" — above a card counting three shared words. Both call the one helper now, and the CLI prints each moment's `kind` (`_moment_line`) because the kind is what carries the epistemic weight and the page shows it as a chip.

    **The INTENT slot takes structural antecedents only** (`_structural_intents`): the `Read` that delivered the file, or the agent's narration immediately before it. It used to take whichever assistant paragraph scored highest on the block's keywords, which is how Decision Memory ended up narrated by YIN pitch-detection math. `_ranked_topical_segments` survives for `_classify_pair` alone — a duplicate pair only asks whether the topic was live — and must never fill a card again.

    **Thinking text is read, and its absence costs nothing** (`_thinking_corroboration`, and `chronological_segments` no longer hardcodes it empty). Availability is mixed per model and CLI version: officially the field is encrypted and empty, empirically 43 of 82 blocks were readable in a recent famigo transcript, so both shapes arrive and the encrypted-gap card in `_moments_for_read_driven` counts only the unreadable ones. The join is on `_thinking_join_tokens` — the skill's own `/name`, the paths the block names, the whole commands it spells out — never on `_block_keywords`: prose overlap matched an `/implement-plan` pointer on the words "agent" and "review" in this repo's own logs. Thinking is deliberately absent from `assistant_text_segments`, so it can never reach `all_assistant_text` and move a keyword verdict; measured faithfulness is under 20%, and a signal a transcript may or may not carry must not decide a status.
8. **Verdict** (`assess_block`) — combines predicates and moments into a judgment with cited evidence, over a **7-status taxonomy** split into two families:

    - USED: `used`, `used-partial`, `possibly-referenced`, `ignored`
    - NOT-USED: `undelivered`, `unused`, `dormant`, `not-loaded`

    Evidence comes in **two tiers**, and the tier caps the verdict. **Strong** evidence ties the block to a specific observable outcome: a trigger the user actually typed (`trigger`), one of the structural joins from step 6 (`skill-invocation`, `writes-to-named-path`, `template-echo`, `command-echo` - each a record of what the run did, tied to something the block itself names), or a reviewed compiled check that ran (step 8b). Every one of those is either a harness record or a human-reviewed check, so a rule worded differently - or written in another language - is judged the same way. Only strong predicates can produce `used`, `used-partial` or `ignored`. **Weak** evidence only observes that something the block happens to name occurred, with no causal link back to the block: a bare `command-mention` (whose `matches` is unconditionally true) or the loose keyword fallback (2 of the block's first 8 five-plus-letter words appearing anywhere in the assistant's text, which common words satisfy almost always). Weak evidence tops out at `possibly-referenced`; it never reaches green. A block with predicates but nothing applicable stays `dormant`, and a block with no signal at all stays `unused`, exactly as before. `_is_strong` / `_fired_strongly` are the shared helpers, and `_fired_strongly` insists on strength **and** `applicable` **and** `matches` together: `matches` alone is true for every command mention.

    Applicability and **exercise** are separate questions. Applicability asks whether the rule's precondition was met; exercise asks whether the run did the kind of thing the rule is about. They part company for a cwd-conditional rule: without the distinction a turn that ran no `gh` command at all was reported as a GitHub-account violation, which is how a dozen compliant turns ended up under a red session badge. The question now lives in `rule_checks`, which answers it from the corpus rather than from prose - `_antecedent` / `_in_scope`, and the `not-exercised` block state (step 8b). On the predicate side the contract survives as `_is_exercised` plus the optional `exercised(trace)` callable, and **no current kind supplies one**: the retired `path-table` was the only predicate whose precondition (the cwd) could be met without the rule being exercised, and every remaining kind's precondition *is* its exercise (a trigger that was typed, a file that was written, a command that ran).

    `combine_verdicts` ranks the statuses `used` > `used-partial` > `possibly-referenced` > the NOT-USED family, so the invariant "used in any turn -> used at session scope" still holds and weak evidence can never outrank real evidence. `ignored` is the exception to a plain ranking: it wins over the NOT-USED family, but a scope with **both** `ignored` and `used`/`used-partial` turns combines to `used-partial`. One mis-scored turn used to repaint a session over a dozen provably compliant ones, and `ignored` at session scope has to mean what it says - the rule applied and was satisfied nowhere. The downgrade hides nothing: `used-partial` is not green, the violating turn stays red at turn scope, and the aggregate's reason counts the turns. Every `ignored` reaching the combine is exercised by construction, because `assess_block` refuses to say `ignored` without exercise.

    The aggregate's reason is regenerated from the combined status (`combined_reason`) wherever the combine rule overrules the aggregate's own assessment. The two were computed independently, so one real record read status `ignored` above the reason "1 predicate(s) applied and were satisfied" - three realities in one row. Moments and evidence keep their session-wide assessment, which is still the most informative view at aggregate scope.

    Delivery is checked before predicates run: `_delivery_range` records `delivered_ranges` as a list of merged intervals (`delivered_from` / `delivered_to` are only its outer bounds), so a file read as two disjoint ranges marks blocks in the gap `undelivered` instead of scoring text the model never saw.
8b. **Rule checks** (`rule_checks.py`, wired in through `assess_block` -> `_rule_check_for` / `_apply_rule_check`) - the only mechanism that may call a rule *violated*. See "Rule checks" below. Each block may carry a `ruleCheck` record; a confirmed violation from a reviewed checks file (confidence `high` or `medium`) is what turns a block `ignored`, citing file, line and matched text in the reason.

    **A compiled check also gives credit, and only from its satisfied stage.** A conditional kind whose antecedent fired and whose consequent happened (`stage == satisfied`, from a checks file, medium or high confidence) lifts the block to `used`, and a `not-exercised` record folds an `unused` block to `dormant` - which is what `dormant` says. Both exist because step 6 no longer derives a strong predicate from prose: without them a session that obeyed a compiled rule a dozen times read `unused`, and one violating turn then repainted the whole session `ignored` at the combine, which is F-COMBINE coming back through the new mechanism. The credit is deliberately narrower than `clear`: `clear` also covers "the checks matched nothing", which for a forbidden-pattern rule over a coarse scope (any bash command at all, for a shell kind) is the absence of a violation rather than evidence the block was followed. A `fallback` (mechanically extracted) record gives neither credit nor blame, exactly as before.
9. **Token attribution** (`attribute_request`, `attribute_usage`, `block_costs`, `history_chars_by_request`, `_annotate_costs`) — splits each request's reported prompt tokens across the context items that were resident for it, proportionally by character size, plus a remainder bucket sized by the conversation prefix so file figures aren't inflated by chat growth. Rolled up per file into `cost` (`sentCount`, `tokens`, `cached`, `fresh`): the same file is resent on every request, which is where the real money goes. The cached/fresh split comes from the request's own figures. Files evicted by a compaction stop accruing from that request onward (`_nonresident_by_request` lifts the per-turn residency onto requests by event index). Rounding uses the largest-remainder method so the parts always sum back to `usage`'s `promptTokens` exactly. Per-block figures (`block_costs`) divide a file's cost by line share and always carry `estimated: true` — the UI must label them.
10. **Duplicate detection** (`compute_duplicates`, `_classify_pair`) — n-gram shingle containment across all loaded context files, classified as `redundant` / `overlap` / `related`. `_classify_pair` applies the same evidence tiers as step 8: a pair falls back to `referenced` only on a strong predicate that genuinely fired (`_fired_strongly`) or a strong topical reference, so a pair carrying nothing but bare command mentions is honestly `redundant`. Pair costs come from step 9, not from character counts: `tokensA` / `tokensB` are each block's attributed cost across every request that carried it, and `tokens` is the overlapping share of the cheaper side (the part that could have been deleted). A pair involving a file that was never sent costs zero, which is the honest answer.
11. **Timeline + file activity** (`build_timeline`, `file_activity`).
11b. **Per-file rollup** (`_annotate_activity`, `_annotate_rollup`, `_violation_headline`) - what the drill-down's File and Turn levels read. Each context-file record gains `activity` (`reads` / `edits` in this scope) and `rollup` (`statusCounts`, `active`, `summary`); each turn record and each `data.sessions[]` entry gains a `headline`. `activity` joins the raw absolute `file_path` a tool input carried to a context file's `abs_path` by resolving **both** sides (`_resolve_key`): the display path is the tilde form, and an unresolved join reports every file as untouched, which looks plausible. A file is `active` when it was read or edited in the scope or any of its blocks has a status in `ACTIVE_BLOCK_STATUSES`; everything else, `not-loaded` included, is quiet. `summary` is first-match, so it names the most consequential thing that happened rather than a generic tally. `process_session` re-runs `_annotate_rollup` over the aggregate after the per-turn status-combination patch, or the aggregate's file summary would contradict the block list beneath it.
12. **Per-session assembly** (`process_session`) runs steps 3–11b once per transcript, producing a `summary` (lightweight, for the picker) and `per_session` (the full data the active view needs).
13. **Session compare** (`compare_sessions`, `align_actions`, `compare_context_files`) — only when `--compare A B` is passed. Reduces each turn to its ordered tool-call names (read back off the baked turn timelines, `turn_actions`), aligns the two sequences with `difflib.SequenceMatcher` (`autojunk=False`, because tool names are exactly the high-frequency tokens autojunk would discard), and emits paired/unpaired steps plus deltas for tool calls, edits, tokens and per-block verdicts. Never align by index: one extra call early on shifts every later index and would report the whole tail as divergent. Turn *rows*, by contrast, do pair by ordinal — a turn is anchored to a human prompt, so turn N is the same instruction on both sides. Context files are diffed block-wise by the stable block IDs; a file whose block content changed is flagged `drifted`. A pair whose first prompts differ is flagged `sameTask: false`, because deltas between different tasks mislead. `build_data` attaches the result under a top-level `compare` key; without the flag the key is absent and the payload is byte-identical to a pre-compare build.
14. **HTML emit** (`main`) — JSON-serializes everything, escapes `</` and `<!--` so it survives the surrounding `<script>` tag, and substitutes it into `HTML_TEMPLATE` (the giant raw string at the bottom of the file). Output is one self-contained file with a vanilla-JS frontend that renders panels from the baked-in JSON.

15. **Query mode** (`cmd_query`, `run_query`) — `--query` stops before step 14: it bakes the same payload (`select_transcripts` + `bake_sessions` + `build_data`, shared verbatim with `main`) and prints plain text instead of writing HTML. It renders only what is already baked, so the CLI and the page can never disagree.

### Where things live in the script

- CLI args: `parse_args` (~line 4260), with `_split_query_argv` just above it.
- HTML/CSS/JS template: `HTML_TEMPLATE` raw string starting around line 5658 to EOF.
- Multi-session baking is on by default (`--all-sessions`, capped at `--max-sessions 20`). The active session is marked `activeSessionId`.

### The Blocks view is a drill-down

The Blocks view navigates by descending sessions -> turns -> files -> blocks, one level per click, with a breadcrumb and a collapsed ancestor bar per level above the current one. There are no session or turn dropdowns and no file-tree aside; the file list is a level.

- One state object, `nav = {sessionId, turnId, agentId, filePath, blockId}`. **Level is derived from it (`currentLevel()`), never stored.** `navigate(patch)` is the only writer: it merges the patch, nulls every deeper field, syncs `activeSessionId` / `activeTurnId`, rewrites the hash and re-renders.
- `activeTurnId` is **app-wide scope, not the Blocks view's alone**. Timeline, Files and Duplicates all read `activeTurn()`, so navigation that leaves it behind makes those tabs silently show a different turn than the verdict just read.
- A session whose `turnCount` is 1 skips the turn level in both directions: descending into it lands on its file list, and ascending from that list leaves the session.
- A subagent hangs off its turn **at the same rank as a context file**: `agentId` is a peer of `filePath`, not a level below it, which is why it is not in `NAV_KEYS` (the ranked walk cannot express two fields at one rank, so each of the two clears the other explicitly). `currentLevel()` returns `'agent'` when it is set, and the agent screen replaces the file list at its level rather than the whole layout, so the breadcrumb, ancestor bars and scope badge stay put. Both of an agent's tiles - the send-off and the report-back - carry the identical patch `{turnId: <spawn turn>, agentId}`: seeing the two as one run is the point. Escape from the agent screen goes back to the turns list, which is the only place it can be opened from.
- The hash is `#s=&t=&a=&f=&b=`, written with `replaceState` (`pushState` would make the back button walk the descent one row at a time) and re-read at boot. `a=` and `f=` are peers and are never both written, so `navFromHash` resolves the agent first and returns. Parsing never throws: each level resolves against the baked data or the walk stops there, because a blank pane leaves the reader no way back. `navFromHash` adds the `agentId` key to the path **only when it resolves** - a patch merely *containing* `agentId` clears `filePath` and `blockId`, so returning a null one would strip every file deep link on boot.
- Files and blocks render in an Active group above a Quiet one, from the baked `rollup.active` and the `ACTIVE_STATUSES` mirror of `ACTIVE_BLOCK_STATUSES`. Both are always rendered; it is a classification, not a filter.

### Rule checks (`rule_checks.py`)

**The tool never calls a model and never makes a network request.** A prose rule is interpreted exactly once, *outside* this tool, at authoring time.

**Compile step (`/compile-rules`, outside the tool).** [`.claude/commands/compile-rules.md`](.claude/commands/compile-rules.md) is the slash command; [`prompts/translate-rules.md`](prompts/translate-rules.md) is the authoritative flow it follows, and the command deliberately points at the prompt rather than restating it. The flow extracts every rule as its own record, classifies it into a bucket, generates patterns plus fixtures plus both example lists, verifies them, writes `<doc>.checks.json` beside the document (e.g. `CLAUDE.md.checks.json`; `<stem>.checks.json` also resolves), and then **stops at a review gate**: it names the file and the per-bucket counts and does not commit it. That file is a reviewable repo artifact whose patterns run as written on every later audit - read it before trusting it. Expect it to refuse most rules: across four real guideline docs an earlier version of the prompt produced 32 checks and correctly marked 69% of rules `not_checkable`. That refusal rate is the design working, not a failure.

A statement the prompt makes about the corpus, the vocabulary or the loader's gates is part of the contract: `tests/test_compile_flow.py` asserts the prompt names every v2 field and closed-set value the loader enforces, because a prompt that omits one compiles a record that is refused at load and nothing at check time can say the prompt was the cause.

**The first audit is the onboarding step** (`_rule_compile_rollup`, `rule_checks.compile_state` / `compile_status`). A rule with no reviewed record reports `not-checkable`, which reads as a limit of the tool when the truth is that nobody has compiled it yet - so every report counts the project's rule documents and names the command. `compile_state` decides one rule's state - `compiled`, `stale`, `refused`, `uncompiled` - and **both the session-wide counts and each block's `ruleCheck.hint` read it**, or a document reported fully compiled could sit above a block asking the reader to compile that very rule. `refused` is an answer the compiler gave and this tool can report (an explicit `not_checkable`, or a bucket parked for the judge tier), so it carries no hint; a record that did not survive the loader (stale, demoted, rejected) is `uncompiled`, because re-compiling is the fix. The rollup is baked from the aggregate payload only (`summary.ruleCompile` carries the counts and the hint, `per_session.ruleCompile` adds the per-document breakdown): the documents on disk are a property of the project, not of a turn. The analysis side never runs the compiler, so the offline guarantee is untouched.

Which blocks count as rules is `_looks_like_a_rule` / `RULE_CUE_RE`, and its cue set has to be a superset of every cue an accusing or typing mechanism reads: the mechanical fallback's `NEGATION_RE`, and `classify_block`'s `Rule:` label. A self-labelled `**Rule:**` block that the counts did not see was a rule nobody was ever told to compile - which is exactly what the gh-account block became the moment its bespoke predicate was retired, reporting nothing at all. (The cue set is English, and moving rule-cue detection to authoring time is §4 item 3 of the research doc; being wrong here costs a missing hint, never a verdict.)

**Checks-file format.** `{"source", "checks": [...], "not_checkable": [...]}`. Each check carries `id`, `rule_ref` (the heading it belongs to, or a line number), `rule_text`, `domain` (`source` | `shell` | `path` | `tool`), `kind` from the closed vocabulary in `rule_checks.VOCABULARY`, its pattern fields, `applies_to` globs, `confidence`, `message`, and a mandatory `self_test` with both `should_match` and `should_not_match` (`fixtures` is the v2 name for the same object). An optional `rule_key` (from `rule_checks.rule_key(heading, text)`) pins the check to the exact rule text it was written for: if the rule is edited the key stops matching and the check is skipped as stale rather than applied to wording it never read.

**Record format v2** (research doc §8). Every v2 field is optional, so a v1 checks file loads and reports exactly what it always did - the fields say what a record *is*, and a file that says nothing is read the way it was. A record may declare `statement` (the rule as one testable question), `scope` (`code` | `communication` | `process`), `evidence` (`diff` | `files` | `transcript`), `bucket` (`deterministic` | `hybrid` | `judged`), and `examples_positive` / `examples_negative`. A value outside its closed set is refused rather than ignored, and so is an `evidence` the kind cannot read (a source pattern over the tool log, a tool pattern over a file's text): a check reading nothing reports as a rule nothing triggered, which looks like honest silence instead of a broken record.

**Buckets, and what a failing fixture does.** `deterministic` is the only bucket this tool can decide. `hybrid` (sites enumerated here, each judged in isolation) and `judged` are parked in `loaded["judged"]`, applied to nothing, and reported on the block as unchecked with the bucket named - a rule nobody could check must never render as one that was followed. A **deterministic record whose fixtures fail to reproduce here is demoted to `judged` and says so** (`loaded["demoted"]`, carrying `fromBucket`): the point of re-running fixtures is that a broken check becomes visible as a broken check, so a silent drop would defeat it. A record with no `bucket` field is a v1 record and is still *refused* on a fixture failure - taking the demotion path for it would change what every existing checks file reports about itself. Both lists ride on the block's `ruleCheck` as `demoted` / `judged`, beside `stale`, and both the page and `--query` name them: "its fixtures are broken", "no judge ran it" and "this rule cannot be expressed" are three different facts, and a reader who cannot tell them apart cannot tell which one to fix.

**Evidence scoping: the net diff, not every hunk.** `build_corpus` returns `final_code` beside `code` - the same paths after every write is replayed against the others (`_net_code`, `_apply_edit`), so an `old_string` the buffer already holds is *substituted* rather than appended and a revert reads as a revert. Source and candidate kinds read that net diff by default, v1 checks included (`_source_entries`): a rule about code is a rule about the code that ended up in the tree, and 3-19% of what the eight baseline sessions wrote never survived to it - text a check scanning `code` could have accused the agent over, in a file where the reader would go looking and not find it. `evidence: "files"` opts back into every hunk, for the rare rule about what was written at all. `_in_scope` reads the same corpus the check does, or an empty net diff would report `clear`.

**Omission rules need a candidate search.** A rule like "always implement the catch body" is broken by writing *nothing*, so the pattern that would catch it is absent by definition - the external spec calls a missing candidate search the most common source of a false "all clear". `enumerate_candidates(kind, entries, globs)` extracts the sites instead, from `CANDIDATE_KINDS` (`catch_block`, `comment`), each carrying path, line, the text to quote and its own body separately. `catch_block` reads the comment-stripped view, so a commented-out `catch` is not a site and a comment-only body reads as the empty body it is; `comment` derives its spans from the same central stripper (via a sentinel fill) rather than re-parsing, because a second matcher for one question is how block-comment continuation lines were missed the first time, and a file whose extension names no language yields nothing. The `candidate_requires` kind cites any site whose own text fails its pattern; no site at all is `not-exercised`, never `clear`. The strict-vs-stripped agreement rule above does not apply to it and does not need to: the site is extracted from the stripped view, so it cannot itself be inside a comment, and its body is matched stripped because a token that appears only in a comment is not the rule being satisfied. The opt-in judge tier asks its question about these same records - one enumeration, or the deterministic half and the judged half disagree about which sites exist.

**What load time enforces.**

- **Self-tests are re-run here** with this tool's matcher, and any check that fails is refused and reported as `not-checkable`. The pilot found a check that passed the generator's own verification and failed the consumer's, because the two disagreed about `required_order`; a generator's claim that its tests pass is not evidence. A tool kind's self-test snippet is itself a tool log - one call per line, in order (`_selftest_tools`) - because an ordering check that could not be given a sequence could not be tested at all, which is the one thing this gate exists to catch.
- **Comments and string literals are stripped centrally** (`strip_comments_and_strings`) before any pattern runs, self-test snippets included, preserving offsets so spans and line numbers stay true. Per-pattern comment guards are explicitly *not* the mechanism: a line-anchored guard cannot see the continuation lines of a block comment, which is how the pilot false-positived inside a CSS comment.
- A finding is `violated` only when the strict match and the match over stripped text **agree**; disagreement is `unclear`, never a violation. Every violation carries a citable span (path, line, matched text, check id): a candidate without one is not reportable.
- An inline `ctx-allow` marker (optionally `ctx-allow: <check-id>`) on the match's line or the line above downgrades a finding to `acknowledged`, for the deliberate exception with a documented rationale.

**The tool log and the tool kinds.** `build_corpus` returns a fourth shape beside `code` / `commands` / `paths`: `tools`, every call in call order carrying its own `index`, so ordering and counts are decidable. `commands` and `paths` are unordered sets of facts, which is why "check the account before running `gh`" could not be expressed over them at all - and ordering constraints are where the research puts ~73% of real agent failures. A call is one **line**, `<ToolName> <arguments>`, and every tool pattern matches that line (`arg_pattern` alone matches the arguments without the name). Two exclusions keep the line honest: written file contents, because a whole file pasted into a line makes every citation it anchors unreadable, and the human-facing `description` a Bash call carries, because it is prose *about* the call - with it in the line, the real label "Check active gh account" matched `gh <word>` and condemned the very call that complied.

The kinds are `tool_forbidden`, `tool_required`, `tool_precedes`, `tool_never_without_prior`, `tool_arg_matches`, `tool_call_count` and `writes_to_path`. `tool_required` and `writes_to_path` take a `trigger_pattern` rather than standing alone, and `tool_call_count` refuses to fire when its pattern matched nothing, for the same reason in each case: an obligation that simply never happened has no call to quote, and a violation without a citable span is not reportable. The cited call is always the one that went wrong - the `gh` with no prior check, the call that jumped the queue, the first call past a `max_calls` limit, the trigger whose obligation went unmet.

`tool_required` is deliberately **order-blind** - it asks only whether both things happened - so "before"/"after" belongs to `tool_precedes`, and "after *every* edit" is not expressible at all and must go to `not_checkable`. The authoring prompt says all three, because the natural mis-encoding produces a green badge over a session that did the two things the wrong way round.

Two things the tool kinds get right only because they were measured against the real anchors. **A prior earlier within the same line counts** for `tool_never_without_prior`: agents write "check, then run" as one compound Bash call (`gh auth status …; gh pr list`), so comparing call indices alone condemned the most compliant shape there is. And **a satisfied or unfired stage note must not spend the finding limit** (`_capped`) - a tool kind reports its stage even when nothing is wrong, so twenty quiet rules on one block would otherwise stop the twenty-first from ever being evaluated and drop the only real violation.

**Two-stage conditional reporting.** Every finding from a *conditional* tool kind carries a `stage`: `antecedent-not-fired`, `consequent-missed` or `satisfied` (`rule_checks.STAGE_*`). `tool_forbidden` carries none, deliberately: the call happening is the whole finding, and labelling it a missed consequent tells the reader an obligation went unmet under a badge that is about an action being taken. Over 30% of real conditional failures are wrong condition-checking rather than a wrong action, so which stage failed *is* the finding, and an antecedent that never fired is a different fact from a consequent that was missed. The unfired one is the only finding with nothing to cite (`line` 0, empty `match`): picking some other call to point at would put a citation under a claim no call supports. `_in_scope` asks each tool check's own `_antecedent`, so the block state agrees with the stage - a rule whose trigger never came up is `not-exercised`, never `clear`, because `clear` reads as "the rule was followed" when the truth is that it was never tested.

**Block states** (`ruleCheck.state`): `violated`, `acknowledged`, `unclear`, `clear` (checks ran over in-scope code and found nothing), `not-exercised` (the session wrote nothing the checks apply to, a conditional's antecedent never fired, or an omission rule found no candidate site), `not-checkable`. A rule that could not be checked says so and is never rendered as followed.

A checks file is trusted repo content: its patterns run as written, with no timeout, so review a generated one before committing it - a pathological regex would hang the build.

**Fallback.** A guidelines document (`kind` in global / project / rule) with no checks file falls back to mechanical extraction: a negation cue followed closely by a backticked, code-shaped token, scoped by the globs the block names or, failing that, to known code extensions only, and matched only against written code. Everything it produces is `confidence: "low"` and never turns a block red. Files the agent merely read get no fallback at all: reading a file does not make its prose a rule.

### Conventions specific to this codebase

- The script must stay **stdlib-only**. Don't add dependencies.
- The tool must never call an LLM or make a network request. Rule interpretation happens at authoring time and its output is a checked-in JSON file this tool merely reads.
- All UI changes go inside `HTML_TEMPLATE` — don't split the template into a separate file. Self-contained output is a hard requirement.
- When adding new data to the JSON payload, mirror the existing per-session vs. session-summary split: cheap metadata in `summary`, heavy data in `per_session`. The picker reads summaries; only the active session's full data needs to be "live". Token usage follows this split: `summary.usage` and `per_session.usage` carry the totals dict (`requests`, `inputTokens`, `outputTokens`, `cacheReadTokens`, `cacheCreationTokens`, `cacheCreation1hTokens`, `cacheCreation5mTokens`, `thinkingTokens`, `promptTokens`), each turn payload carries its own `usage` of the same shape, and the per-request `usageSeries` lives in `per_session` only. Attribution follows the same split: `summary.contextTokens` is the one cheap roll-up, `per_session.attribution` (and each turn's) carries the per-file breakdown and the history bucket, and each context file's `cost` / each block's `cost` ride along with the file records.
- Payload changes are **additive only**: every existing key in `data`, `data.sessions[]`, `data.perSession[]` and each turn record keeps its name, position and value, and new keys are appended. `tests/test_rollup.py::test_payload_is_purely_additive` holds the line against a committed golden payload. This replaces the older "single-turn output is byte-identical to before" invariant, which the drill-down deliberately broke: the payload is the stable contract, the rendered HTML is not.
- Any value the UI shows must be **computed in Python and baked**. `--query` renders only what is already baked, so a rollup invented in JavaScript would put the CLI and the page in disagreement the moment someone asks the CLI the same question.
- Block IDs use `file_slug(path) + "-" + index + "-" + title-slug`, and a context file's own `id` is the `file_slug` half (turn-scoped records prefix both with `turnN-`). Keep both stable across runs - block ids are how the frontend addresses a block and how the deep-link hash names one (`b=`), and file ids are how `--query` addresses a file. The hash's `f=` still carries the display path, which predates the file id.
- Agent rows in the turns list are `.agent-row`, deliberately not `.drill-row`: the drill click handler parses `data-nav`, so a row that navigates nowhere must not match it. Lane occupancy per row is *computed* by walking the baked `turnRows` once (`laneLayout()`), never authored per row - authoring it is what broke tracks across other agents' rows in the prototype. A figure a notification never carried renders as an em dash, never as `0`.
- The `kind`/`scope`/`group` taxonomy on context files drives the file grouping (read / project / global). New file sources should pick an existing kind before inventing a new one.
- The escape pair `.replace("</", "<\\/")` and `.replace("<!--", "\\u003c!--")` in `main` is load-bearing — both sequences would otherwise break out of the `<script>` block. Don't remove.
