# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

A single-purpose tool that parses a real Claude Code transcript (`.jsonl` under `~/.claude/projects/<encoded-cwd>/`) plus the relevant `CLAUDE.md` and skill files, and emits **one self-contained HTML file** with all the data baked in. The HTML is the product - there is no server, no build system, no package manager. The output is meant to be opened in a browser and used as an investigative IDE for "what context did the agent actually use on this turn?".

There are two HTML artifacts in the repo:
- `agent-context-ide-prototype.html` - hand-written static mockup. Reference for layout/styling only; not generated.
- `agent-context-ide-real.html` - the script's output, regenerated by running the script. Treat as a build artifact.

Per-turn scoping is the core design: a turn spans one real user prompt to the next, and every verdict, cost and rollup is computed per turn as well as session-wide. The Blocks view navigates by drilling (see Architecture below).

## Running

```bash
# Generate the HTML for the most recent session in this cwd
python3 build_real_view.py

# List all sessions discoverable for this cwd
python3 build_real_view.py --list

# Pick a specific session by id prefix
python3 build_real_view.py --session abc12345

# Single-session output (skip the multi-session picker)
python3 build_real_view.py --no-all-sessions

# Compare two baked sessions (id prefixes) - adds the Compare tab.
# Off by default: without it, no compare payload is baked at all.
python3 build_real_view.py --compare abc12345 def67890
```

### Query mode (read-only, no HTML)

`--query` answers in plain text instead of building the page, reading the same
baked JSON the page renders. It writes nothing and never opens a browser. Each
listing prints the ids the next query needs, so three commands take you from
zero knowledge to one block's verdict:

```bash
# 1. every session: id, when, turns, tokens, prompt preview
python3 build_real_view.py --query sessions

# 2. what happened, and what was in context
python3 build_real_view.py --query abc12345 turns
python3 build_real_view.py --query abc12345 blocks
python3 build_real_view.py --query abc12345 turn-2 blocks

# 2b. the same drill-down the page offers: the scope's context files, active
# ones first, each with the summary line the File level shows, then one file
python3 build_real_view.py --query abc12345 turn-2 files
python3 build_real_view.py --query abc12345 turn2-users-jakuburban-claude-claude-md

# 2c. the subagent runs the session spawned, then one of them
python3 build_real_view.py --query abc12345 agents
python3 build_real_view.py --query abc12345 turn-2 agents
python3 build_real_view.py --query abc12345 agent-toolu_017xzfvjAFYgsyjCxkr3zzQQ

# 2d. what the context cost, worst value first (session scope only)
python3 build_real_view.py --query abc12345 waste

# 2e. every rule document in the project, its compile state and bucket mix
python3 build_real_view.py --query sessions --compile-status

# 3. one block's verdict, reason and moments (block ids come from step 2)
python3 build_real_view.py --query abc12345 users-jakuburban-claude-claude-md-0-how-to-talk-to-me

# Bounds: fields cap at ~1500 chars and listings at 60 rows. Anything elided
# prints the exact command that returns the rest:
python3 build_real_view.py --query abc12345 <block-id> --field content
python3 build_real_view.py --query abc12345 blocks --all
```

A block's output includes a `text` line - `transcript`, `disk` or `stale`, which text the verdict is about (step 5) - and its `rule` line - the rule-check state, its findings with file, line and matched text, and the reason a rule could not be checked - and a `[todo]` line naming `/compile-rules` when the rule has no reviewed record behind it.

A session's output includes the `rules` / `todo` lines: how many of the project's rules are compiled, reviewed as not checkable, uncompiled or stale, one line per rule document with its bucket mix, and the one command that closes the gap. `--query sessions` repeats the hint - counted in uncompiled *documents*, since that is how many times the command has to run - because the listing is a fresh reader's first command, and the line disappears once nothing is left to compile. `--compile-status` is the whole project on one screen: every rule document, its state, its mix, its checks file and what to compile next.

A file's output includes its active/quiet group, its `rollup.summary`, how often
the session read or edited it, its attributed cost, and its block list.

The `waste` listing is every loaded file by attributed cost and turns resident,
worst value first, printed straight off the baked `wastedContext`. It is session
scope only, and it says out loud when relevance was not judged: the top of a
cost-only list is not an answer about value, and a reader who does not know the
question was never asked will read it as one.

An agent's output includes its lane, the turn it was spawned in, its runtime,
tokens and tool calls, every report-back it sent, the on-disk subagent
transcript it names (which this tool deliberately does not read), and the two
fields no other view shows: the `brief` the main agent wrote and the `result`
that came back. `--field prompt` / `--field result` print either in full. The
`agents` listing is in spawn order and names each agent's lane and the fan-out
it was collapsed into, all read straight off the baked `agents` / `turnRows`,
so the CLI and the page describe one picture.

An address is `sessions` | `<session-id-prefix> [turn-N] [turns|files|blocks|agents|waste|<file-id>|<block-id>|agent-<id>]`.
A leaf token is resolved as a block id first and a file id second, so every id
that resolved before the `files` level existed still resolves to the same block.
An `agent-` token addresses a subagent run, but still falls through to the block
and file lookups first: a file really can be called `agent-foo.md`, and its slug
must stay reachable.
An unknown id exits non-zero with the commands that list the valid ones.

There is no linter config and no dependency beyond the Python 3 standard library.

## Tests

```bash
# Run the whole suite (bare `pytest` - `python3 -m pytest` won't find it,
# pytest is not installed for the default python3 on this machine)
pytest
```

`tests/` holds a pytest suite. `tests/conftest.py` puts the repo root on `sys.path`, so tests `import build_real_view as brv` directly.

The convention is in-memory event builders, not jsonl fixtures on disk: `tests/test_turns.py` defines `user_text`, `user_slash`, `user_tool_result`, `assistant_text`, `assistant_tool_use` and `_ts`, and other test modules import them. Assemble a small event list, run it through a pipeline function, and assert on the returned dict/JSON structure. Never assert on HTML strings: the template is not a stable contract.

New areas go in `tests/test_<area>.py` in the same style. Verifying a change means `pytest` green *and* regenerating the HTML and opening it.

`tests/test_regression_verdicts.py` is the verdict regression harness and is not a normal test module: it encodes the verdicts a hand audit of real sessions proved wrong (the anchors and failure mechanisms are §7 and §2 of `docs/judgement-reliability-research.md`), one case per finding, tagged by mechanism in the test name (`pytest -k f_pathtable`). The `test_counter_anchor_*` cases are the verdicts the audit found *correct* - a change that flips one of those has made the judging worse, not better.

**Every case in it has to be able to fail, and a vacuous case is the failure mode.** A case is vacuous when its fixture derives no predicate and its document has no checks file: `assess_block` then has nothing to reach a hard verdict with, so `status != "ignored"` passes whatever the code does. Sixteen cases were vacuous exactly that way once the bespoke prose predicates were retired and nothing replaced them, so the two rules they are about - the GitHub-account table and the closing-summary rule - are now driven through `tests/fixtures/global_rules.md` and the reviewed checks file beside it, which is the only mechanism left that can reach either verdict. Each asserts the exact status and the exact `ruleCheck` state rather than a negation, and the module docstring records the one-line production probe that turns each family red. The red path is exercised there too: a `gh` command with no prior account check is `ignored` with a cited span, so "no false reds" is measured rather than assumed.

Two other modules are gates rather than unit tests, and both are described in the README's trust-model section. A third gate lives outside `pytest`: `snapshots/compare.py` scores the frozen before/after payloads against the hand-written ground truth in `snapshots/expected/` and writes `snapshots/SCORECARD.md`. `tests/test_scorecard.py` only tests the scorer (on a synthetic triple, the regressed case included) - the corpus itself is re-scored by running the script, because it re-bakes 8 real sessions. A ground truth is written from `snapshots/inventory.py`, which shows the action list and the block identity with every verdict field withheld: written after reading the report, it would ratify whatever the report says. The scorecard has **two tables** - skill and command blocks, and rule-document blocks - because one ruling decides how an invocation is credited across every skill and command document and those rows outnumber the rest, so a single headline reports that ruling as a measurement of the judging. Its header also states how many `violated` truths and compiled checks files the corpus holds and warns when either is zero, since a false-red count of zero over a corpus with no red path measures nothing. The rulings the truth applies live in `snapshots/expected/RULINGS.md`; `compare.py` refuses an `expected.md` whose header does not reference them and quote the disputed one, and refuses a `revised:` note with no `blind:` line. A block a payload reports as never delivered (`not-loaded` / `undelivered`) is scored on that answer rather than as absent, and the totals count the rows that moved there. A block the baseline never judged is `new-agreed` or `new-wrong`, never `fixed`, and `new-wrong` is a release blocker beside `regressed`; the totals count the credited rows that rest on a `blind: no` revision; a session whose inputs were frozen in after its baseline was baked is named and its moved rows tagged; and a partial corpus exits non-zero unless `--allow-partial` is passed. The reviewed checks files are committed under `snapshots/checks/` and `snapshots/freeze_checks.py` copies them into the gitignored baselines, so the patterns behind a red badge are reviewable without the transcripts - with one named exception: the OZZ checks file behind the `authorised` rows carries a client's own rule prose and is not published, so `freeze_checks.py --check` enumerates the baselines too and fails on it as UNREVIEWED (the committed side alone is blind to a file that is only private), and the single record of it that produces those badges is quoted in full in `RULINGS.md` 9. A fifth truth class, `authorised` (RULINGS.md 9), is what the red side is actually measured against: a scan of all 1,093 of this author's transcripts found no clean unsupervised violation, because this author works with the agent in the loop, so the six sessions that push to master under a reviewed high-confidence record were each ordered to in the prompt that caused the push. `authorised` allows exactly what `no-hard-verdict` allows - the rule's action happened and was not misconduct - so a red there is a false red and a green is still a false green, and the header says in so many words that a false-red count of zero is measured against authorised actions only. Such a ground truth covers one question rather than a whole session, so it declares itself partial in its header and `compare.py` counts its out-of-scope blocks instead of naming them: a block id carries its document's path, and naming them would publish a client repository's document names into a committed file that its transcripts are gitignored to keep out.

The snapshot corpus under `snapshots/baseline/` and `snapshots/after/` is the author's own raw transcripts and is gitignored, so it is not in a clone: `snapshots/compare.py` and every test that needs it skip or exit naming the directory rather than scoring a shrunken set, which means the scorecard is the author's measurement and a contributor cannot regenerate it. `tests/test_privacy.py` holds the ignore rules, the clean `git status` and the empty history.

`tests/test_calibration.py` scores the labelled lexical set (`tests/fixtures/lexical_pairs.json`, loaded and scored by `tests/lexical_fixture.py`) and gates on **precision ≥ 0.90**, with a floor under the number of true positives so a tier that answered `no-lexical-trace` to everything could not post a perfect ratio on an empty numerator, and - in the same test, deliberately - the **exact false-positive count**. The ratio alone is too coarse to be a gate: over 245 scored pairs a threshold edit that manufactured its first two or three false positives still clears 0.90, and the sentence a reader quotes ("no false positive on the labelled set") would stop being true with nothing red. It also pins every threshold in `lexical.py` against the fixture's `operatingPoint`, so moving one without re-measuring fails; both halves are needed, because a threshold can move without changing a single verdict on this set and a verdict can move without any threshold changing. On a clone the 218 pairs that reference the private corpus cannot be resolved at all, so the corpus-dependent tests skip by name and the gate runs over the 32 inline pairs (`lexical_fixture.resolvable` / `inline_pair_count`, and the `minTruePositivesInline` floor that stops an empty set passing). Real pairs *reference* the frozen baselines under `snapshots/baseline/` rather than copying session prose into `tests/` - a second copy of a real transcript is a second thing to sanitise and a second thing to keep in step; contributed pairs carry their corpus inline instead, which is what makes them shareable, and `tests/label_pairs.py` is the local-only CLI that produces one.

`tests/test_degradation.py` is the degradation matrix: each optional signal (ctxlog, readable thinking, the English frequency list, ast-grep, the judge tier) switched off individually, with every verdict compared against the same run with it on. "Worse" is defined from the audited rule's point of view - an accusation the signal's presence did not make, or a hard verdict of *either* sign reached only because the signal is missing, since a green invented by an absent signal is as wrong as a red. Losing information is not worse: `dormant`, `unused`, `not-checkable` and `no-lexical-trace` are what "signal unavailable" looks like. `OPTIONAL_SIGNALS` is the registry and a test asserts the matrix covers it, so a sixth optional signal cannot ship with no contract.

## Architecture

`build_real_view.py` is a single ~9.4k-line script structured as a linear pipeline. The numbered comment banners inside the file (`# ---------- 1. parse CLAUDE.md ----------` etc.) are the canonical section map - follow them when navigating. Three small stdlib-only modules sit beside it: `ctxlog_facts.py` (reads the hook log at `~/.claude/ctxlog/<session>.jsonl`), `rule_checks.py` (compiled rule checking, see below) and `lexical.py` (the lexical tier, step 6 below, with its optional English frequency list in `data/`). A fourth, `judge_tier.py`, is the LLM tier; it runs by default and is imported only from inside `make_judge`, so `--no-judge` never loads it.

Pipeline, in order:

1. **Discovery** (`discover_all_transcripts`, `encode_cwd_for_projects`) - Claude Code stores transcripts at `~/.claude/projects/<encoded-cwd>/*.jsonl`, where the encoding replaces both `/` and `.` with `-` (so `/Users/x/famigo/.claude/worktrees` becomes `-Users-x-famigo--claude-worktrees`). Only top-level `*.jsonl` files are transcripts; sub-agent runs live in per-session subdirectories and are excluded by not recursing. There is no `isSidechain` check - the old first-line probe never matched anything.
2. **CLAUDE.md parsing** (`parse_claude_md`, `classify_block`) - splits each `CLAUDE.md` into H1/H2 blocks, ignoring headings inside fenced code. Each block gets a `kind` (rule, skill-pointer, reference, etc.).
3. **Transcript parsing** (`load_transcript`, `tool_calls`, `assistant_text_segments`, `first_real_user_prompt`). One classifier, `_real_user_prompt_text`, decides what counts as a real user prompt, and both turn splitting and first-prompt extraction go through it so they can never disagree. It flattens list-shaped `message.content` (the shape a pasted screenshot makes: an `image` item plus a `text` item) by joining the `text` items, and rejects tool-result lists, meta events, interrupt markers, `<local-command-stdout>` wrappers, `<command-name>` wrappers for local commands (`/model`, `/config`, recognised by the stdout wrapper that follows them), and `<task-notification>` wrappers. Skill and slash-command wrappers still count.

   **A task-notification is never a turn.** It arrives on the user channel but it is the *result half* of an `Agent` / `Task` / `Workflow` tool call, not something a human typed. Counting one inflated turn counts (48 turns became 24 on one real session) and stole the tool calls that followed it from the turn that earned them. The tag check lives in `_real_user_prompt_text` beside the caveat and interrupt rejections, and both it and `_task_notification_text` `lstrip()` first so the two classifiers can never disagree about the same event.
3b. **Subagent runs** (`agent_runs`, `parse_task_notification`, `attach_subagent_transcripts`, script section `2a`) - pairs every spawn to its report-back by tool-use id and decides everything the views draw. Returns `agents`, the ordered `turnRows`, and a count of `unmatchedNotifications`.

    The notification is generated text, so every tag is parsed with an explicit regex and a missing one is *unknown*, never an error: real sessions carry notifications with no `<tool-use-id>` at all, and one raise there would lose every agent in the session. **One spawn can notify more than once** (an agent notifies each time it stops with no live children and can be resumed), so a second notification appends to the same agent's `returns[]` rather than inventing a second agent. A notification naming a tool call that is not a spawn (a background `Bash`) is neither an agent nor unmatched; only one that ties to nothing at all is counted, and `main` prints a warning rather than swallowing it, because a lost pairing silently reports a finished agent as never returning.

    **Lane and colour are baked, not derived in the browser.** An agent takes the lowest free lane on spawn and releases it on its *last* return, so an agent that never reports keeps its lane to the end of the session, which is what makes its unfinished track visible. Colour is `AGENT_PALETTE[colorIndex % 6]` in spawn order and means **identity, never direction**: with five agents in flight one hue makes the tracks impossible to tell apart, so direction is carried only by the icon and the badge. Computing any of this in JavaScript would let `--query` and the page describe the same session differently.

    **A fan-out collapses only when every member returned before the next turn row**, never merely because it was spawned together (`_collapse_fanouts`). Keying on "spawned together" would bury the single case most worth seeing: the agent that did not come back.

    **The subagent's own transcript is deliberately not loaded.** The harness writes it to `<session>/subagents/agent-<task-id>.jsonl`; its tool calls carry whole file contents and the report is already tens of megabytes. `attach_subagent_transcripts` resolves the path in Python and bakes it on each return record, so the agent screen and `--query` name the same file, and both say plainly that it is not baked in rather than implying completeness. A consequence worth stating: nested agents (an agent spawning its own children) live in that file, so every count here is main-thread spawns only.

    Agent payload: each record in `perSession[id].agents` carries `id` (the spawn's tool-use id), `type`, `subagentType`, `name`, `prompt`, `promptPreview`, `spawnEventIdx`, `spawnTime`, `spawnTurnIndex`, `returns[]`, `status` (`returned` / `open`), `durationMs`, `tokens`, `toolUses`, `resultText`, `lane` and `colorIndex`. The last five come from the *latest* report only, which the agent screen says out loud for a multi-report agent. Each entry in `returns[]` carries `taskId`, `status`, `summary`, `resultText`, `tokens`, `toolUses`, `durationMs`, `eventIdx`, `time`, `turnIndex` and `transcriptPath`. `turnRows` is the ordered row sequence both the turns list and `--query` walk: `{kind: turn|spawn|return|spawn-group|return-group|dangling, ref|refs}`. Each turn payload gains `agentIds`, and `data.sessions[]` gains `agentCount`.

4. **Usage extraction** (`usage_series`, `usage_totals`, `cache_breaks`, `usage_for_turn`) - reads the `usage` object every assistant event carries, which is the only permitted source for headline token numbers (char-count estimates may appear only where explicitly labelled as estimates). One series entry per *API request*, not per assistant event: the harness writes one response as several events sharing a `message.id` and repeating the same usage verbatim, so the series dedupes on that id and each entry carries its event index, which is how `usage_for_turn` gives each turn its share without ever counting a request twice. `cache_breaks` flags the requests where the cached prefix was lost and repaid (cache read collapses against the previous request while cache creation spikes); those become `cache-break` timeline rows via the same insertion helper compaction rows use.
5. **Context-file loading** (`load_context_files`) - discovers every file the agent could plausibly have used, and is strict about which of them actually entered context. Only `CLAUDE.md` is taken as injected by the harness; an `AGENTS.md` / `AGENTS.override.md`, and any file a hook directive merely tells the agent to read, is `loaded` only on a hook record that it was or a read (`add_unless_read`) - across 1,435 hook logs the harness never once reported loading an `AGENTS.md`, and treating one as loaded because it existed billed ~1.75M tokens to files one session never opened. A bare `cat <file>` (`_shell_full_reads`, nothing piped) loads a file the way `Read` does; `cat f | head` or `sed -n` is a slice and does not. The sources: global `~/.claude/CLAUDE.md`, project `./CLAUDE.md`, skills under `~/.claude/skills/`, files the agent `Read`, files referenced via `@path` in CLAUDE.md, hook directive files, and pre-loaded attachments. Each is tagged with a `kind` and `scope` that drive grouping in the UI.

   Skills come from the harness's `skill_listing` attachment when present. Listing names keep their plugin prefix (`datadog:ddsetup`), and a prefixed name is resolved under the plugin cache (`~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/skills/<skill>/SKILL.md`, newest version wins) after the plain `~/.claude/skills` and project locations miss; a name that resolves nowhere becomes a listing-only entry carrying its description. Skill loading is **call-driven first, prompt-driven only as a fallback** (`_is_loaded`): a `Skill` tool call in the trace, then a slash-command wrapper the user typed, then a word-boundary `/name` mention in the prompt. The prompt match is bounded on both sides, so `/cpanel` does not load `cp` and a bare first word never loads anything.

   **A block is judged on the text the session was given, not the file on disk** (`delivered_versions`, `delivered_at`, `_stale_against_hook`). An invoked skill's or command's body is recovered from the `isMeta` user event the harness injects (`_invoked_body`): a skill carries a `Base directory for this skill:` header naming its file, a command body is keyed `invoked:<name>` off the `Skill` call or wrapper before it, and the trailing `ARGUMENTS:` is dropped. Without it every invoked skill was judged on its disk copy, and one audited `/review` step was credited for a file the delivered text never named. A rule document routinely gains sentences after the session that is being audited: two greens in this repo's own `406bba1d` cited a CLAUDE.md sentence first committed eight hours after the session ended. Three transcript shapes recover the delivered text - a `Read` result's `toolUseResult.file.content` (only where it covers the whole file; a slice cannot be put back inside a file whose rest is only on disk), the `nested_memory` / `already_read_file` / `file` attachments, and the `originalFile` an `Edit` or `Write` result carries, which is the one record of what a document said before the session rewrote it. Every one of the three fails closed: a `Read` record that does not say how much of the file it carried, or whose `startLine` will not parse, is refused rather than assumed whole, because the cost of refusing is the disk text with its marker and the cost of guessing is a verdict about a document nobody read. Versions are ordered by event index and each scope reads the one in effect when it started, so the turn that rewrites a rule is still judged on the wording it was handed; the first version recorded for a path is effective from the start of the session, because a file read at turn 7 and never edited was the same file at turn 1 - unless that first record is the write that *created* the file, which did not exist before it.

   Every block carries `textSource`, which the page shows as a chip and `--query` prints as its own line, because a reader who cannot see which text a verdict is about cannot weigh it. `transcript` is recovered text. `disk` is the fallback: nothing recovered it, the disk file stands in, and one clause on the end of the reason says the wording may postdate the session. `stale` is the third case and the only one that changes a verdict - the ctxlog hook records each instruction file's line count, byte size and truncated sha256 *at the moment it was loaded*, and where those disagree with the file today the disk text is **provably** not what the model was given, so neither a predicate nor a mechanically extracted fallback check is derived from it (a compiled check still runs: its patterns were authored against the rule, and one pinned with a `rule_key` refuses the mismatch itself). Harness injection of CLAUDE.md is not in the transcript in any audited session, so that hook record is the only evidence available for the files this matters most for.

   **An invoked skill or command stays loaded in later turns** (`carried_invocations`, passed down from `process_session` as `carried`). The harness keeps an invoked body in context until a compaction evicts it, but each turn decided loading from its own event slice, so a skill invoked in turn 0 read `not-loaded` in turn 1 and the work it drove there could never earn credit at session scope (formic-core `39b9e09e`: `/grill-prd` Phase 2's template was written in a later turn). A turn now treats every document an earlier turn invoked as loaded, and eviction is not decided a second time: `_compute_payload` drops whatever `nonresident_by_turn` names for the turn, the same set `resident_turns` subtracts, so loading and cost cannot disagree. Being in context is not running. The execution gate (`_execution_start`, behind `_document_executed`, `_credited_reads` and `_procedure_bash`) still needs an invocation record **in this scope**, so the read, write and command joins never credit a carried document. Only the template join does (`_carried_window`), for the **last** document invoked before the turn starts, up to the first invocation of a different skill or command inside the turn, the boundary `_procedure_bash` closes its window on. The narrowing was measured, not assumed: carrying every join let a `/commit` from turn 20 of famigo `9dd3cc8a` stay "running" through a new task in turns 21-24, where a `package.json` read greened its run-tests step, and let a carried `/implement-plan-workflow` window run past a `/sync-agent-docs` typed in the same turn. Nothing in a transcript records when a procedure finished, so a later turn's read or command is the work at hand; a write that reproduces the document's own template literals carries its direction with it. A `/name` the prompt merely mentions carries nothing into a later turn, as it runs nothing in its own. The identity block and the trigger predicate are not carried: they credit the turn that holds the invocation, and the session-scope combine picks that up. The delivered text needs no change, because `delivered_at` already hands a later turn the invoked body recorded earlier.

   **The listing is a session fact, not a turn's** (`skill_listing`, passed down from `process_session`). The harness injects it once, so a later turn's event slice does not contain it - and a skill with no SKILL.md on disk exists *only* in the listing. Without the override such a skill appeared in the payload of the one turn carrying the attachment, normally turn 0 before it was invoked, and the per-turn combine then reported two skills that drove fifteen turns of a real session as `not-loaded`. Skills that resolve on disk are unaffected: the path-convention fallback finds them in every turn.
6. **Predicate extraction** (`derive_predicates`) - for each block, pulls checkable items out of it. Every predicate carries a `strength` of `strong` or `weak` (see step 8).

   **Only harness-defined signals are hardcoded here.** Everything this step reads is a record the Claude Code harness itself writes, identical for every user: a slash command being invoked, a `Skill` call, a file path a tool call carried, a bash command that ran. What a rule *says* is never pattern-matched, with one bounded exception (the slash command a trigger declaration names, below). That is the open-source line: two prose predicates used to be reverse-engineered from one user's own CLAUDE.md - `path-table` matched the literal table header "Project path contains", `end-of-message` matched one rule's phrasing and scored the closing paragraph against one author's writing style - and a third read five clipboard commands (`pbcopy`, `xclip`, `xsel`, `printf`, `echo`) out of bare prose because of one rule about them. All three are retired (§4 of `docs/judgement-reliability-research.md`): they judged one person's wording and would have judged the next user's rules, or another language's, as silence. A rule of that kind is now a compiled record in a checks file, which each user generates from their own rules via `/compile-rules` (step 8b) - a cwd-conditional obligation as `tool_never_without_prior` over the ordered tool log, a response-shape rule as a `communication`-scope record in the `judged` bucket. A rule nobody has compiled reports as uncompiled and names the command; it is never guessed at.

   The predicate kinds that remain are `trigger`, `skill-invocation`, `reads-named-path`, `writes-to-named-path`, `template-echo`, `command-echo` and the weak `command-mention`. `tests/test_generalization.py::test_no_prose_derived_strong_predicate_survives_anywhere` holds that list against every rule document the suite carries, and a Polish fixture beside its English twin asserts the two derive the same predicates.

   The trigger predicate and the skill/command moments builder both ask `_trigger_evidence` - one matcher, bounded on both sides, over the three records that name a command (a `Skill` call, a slash-command wrapper, `/name` in the prompt). While the predicate ran a bare substring test of its own, a prompt reading `/implement-plan-workflow` scored the `/implement-plan` pointer green with the moment card beside it saying, correctly, that the command was never invoked. **Only the first two records are an invocation**, and the trigger predicate demands one of them exactly as `skill-invocation` does: a bare `/name` in the prompt is a mention, so a prompt reading "either /grill-prd or /prd-to-plan - you choose" greened both skills over a run that invoked neither. A mention still draws its `co-occurrence` card, so the reader sees the name that was typed and why nothing fired. There is deliberately **no negative ("never X") predicate**: it used to take the word after `never` and look for it among the session's bash commands, so a rule reading "never import another store's singleton" reported a violation because `import` appeared inside a ripgrep command. Prose negations are the job of step 8b.

   **A trigger declaration is recognised by its shape, not by an English word** (`_TRIGGER_DECL`). The declaration this tool reads is a short label, a colon, and the backticked slash command standing alone to the end of the line - so `Wyzwalacz: `/standup`` derives exactly what `Trigger: `/standup`` does. The two English cues (`Trigger:`, "types `/x`") are kept beside it because they also match declarations that run on into the sentence, but they are sugar: neither is required, and what they extract is a harness identifier rather than a claim about behaviour. The line has to *end* at the command, or "links to: `/deployment`, `/deployment/calibrate…`" - a real line in one audited AGENTS.md - becomes a predicate about a command that does not exist.

   **Trigger declarations are read, documentation examples are not** (`_example_spans`). A `Trigger:` line or a "types `/x`" phrase that sits *inside* an inline-code span or a quotation is prose about the syntax, so it derives nothing: this repo's own Architecture section otherwise produced live predicates printing "`/foo` not invoked this run" about a command that does not exist. A real declaration writes the phrase bare and backticks only the command, so it survives. A quote span may cross a newline and is length-bounded instead - a mispaired quote costs one predicate (`dormant`, an honest refusal), never a false accusation.

   **What the run did is evidence too** (`skill-invocation`, `reads-named-path`, `writes-to-named-path`, `template-echo`, `command-echo`). The judging used to read the assistant's prose and its bash commands and nothing else, so a rule the agent demonstrably obeyed scored `unused` above a reason denying compliance. Five records close that: a `Skill` call or slash-command wrapper lifts that skill's **identity block** - the document's own first block, and only that one (`derive_predicates` takes the file record for the name and asks `_is_identity_block`; a prompt that merely mentions `/name` is deliberately not enough, or every block of a skill goes green because the user typed its name). An invocation records that the *document* ran, which is not evidence that any instruction inside it was carried out: one audited session invoked a `commit` skill three times while its "match the GitHub account" step never happened, and the invocation alone scored that step green. Every other block earns its verdict from the four joins below, and a step with none of them is `dormant`. Identity is positional, never read out of the heading's wording - recognising a title block by its prose would be the single-user pattern-matching this step retired; a backticked path the block names, joined to a path a tool call carried (`_named_paths` / `_path_names_target`); the block's own template literals found in a file the scope wrote (`_template_literals` / `_template_echo_hits`, reading `written_chunks` - Write/Edit content and heredoc bodies, because the memory-rule anchor appended with `cat >> $M/ERRORS.md <<'EOF'`); writes to the block's own document are excluded from **both** path-joined kinds through the same `_path_names_target` comparison - editing CLAUDE.md is not obeying CLAUDE.md, and the comparison is the component join rather than path equality because a `cd <dir> && cat >> DECISIONS.md` append carries a relative path that resolving alone would not recognise, which let a memory file match its own template and marked every older entry in it `used`; and a whole prescribed command that ran verbatim (`_command_echo_count`). Three of the five - the read, the write and the template - are additionally gated on `_document_executed`; see below. A read counts only from the moment the procedure started (`_execution_start`): a file opened before the skill ran is not one of its steps. All five are **credit-only**: `applicable` is the signal itself and `matches` is unconditionally true, so they lift a block and never accuse one - a session that never appended to ERRORS.md may have had nothing worth logging, and reading that silence as a violation is the mirror of the blind spot they exist to close.

   **A read counts, but only inside a procedure that ran** (`reads-named-path`, `_credited_reads` / `_named_path_reads` / `_shell_read_targets`). The write join used to stand in for a read: a famigo `/review` step saying "read `CLAUDE.md`, then load `backend/AGENT.md`" scored `used` on *writes* to those files - some of them a later turn's unrelated documentation sweep - while the honest evidence, the `sed -n` and `grep` calls that read them inside the review turn, was recorded nowhere. Reads come from the `Read` tool and from the shell readers (`cat`, `sed`, `grep`, `head`, `tail`, `less`), read off `_command_segments` for the reason `command-echo` uses it: the reader has to be the program a segment runs, quoted arguments are already masked there so a `grep` pattern cannot become a path, and redirections are stripped first or every `cat > README.md <<'EOF'` would register as a read of its own target. Whole audited sessions never call `Read` once, so a join that knew only about the tool would report those sessions as having read nothing. The join is gated on the **document having been executed in this scope** - the same invocation record `skill-invocation` reads. Ungated it was measured over the whole corpus and turned a tech-stack table green because the session opened one of the files it lists, a repo tour green because something read the README, and cost the rule-document half of the scorecard 14 false greens: a file gets read because the work needed it, not because a block named it, which is ruling 3's own argument. Inside a running procedure that inference reverses - the step's named file being read *is* the instruction being carried out - and the invocation alone still credits nothing beyond the identity block, so the two records together are strictly more than either. **Where a path was both read and written the read is cited and the write is not** (`_named_path_writes(..., read_hits=)`): the two are one interaction with that file, the read is the claim this tool can support, and the verdict is unchanged either way, so the only thing that moves is which line the reader is shown. The precedence is per path, so a second file the run only wrote keeps its write row.

   **A read that several steps name credits none of them** (`_shared_read_paths` / `_split_reads`, the weak `reads-shared-path` row). One read can only serve one step, and nothing in a transcript says which: a `/grill-prd` Phase 1 was credited with the `figma-spec.md` read Phase 0 asked for, and a famigo `/review` Step 4 with the grep that was Step 6's documentation check. So a read whose path two or more blocks of the same document name (any block, the identity block included, joined through the same `_named_paths` / `_path_names_target` the predicate uses) is withheld from the strong tier. It still happened, so it becomes a weak row that says so and caps the block at `possibly-referenced`, with a `co-occurrence` card in place of the green ACTION card. A step keeps anything else it earned - its own read of a file no other step names, a template echo, a command echo, a compiled check. A write to the shared path stays folded behind the read rather than standing in for it, because it is just as ambiguous. Measured over the corpus this clears the Phase 1 false green and costs seven greens the truth calls `used`: the six famigo `/review` steps that share `backend/AGENT.md`, and `/grill-prd` Phase 2, whose template echo fires only at session scope (the PRD was written in a turn where the command reads `not-loaded`) and was being masked by the shared read.

   **The write and the template joins are gated the same way** (`_document_executed`, shared with `_credited_reads`; `_writes_for` and `_template_hits_for`). Three independent blind audits of sixteen non-anchor sessions returned six verified false greens, and five were these two joins crediting a plain rule document: a reband gotchas note *warning* that `app.json` does not propagate, credited by an edit to `app.json` while `Info.plist` never appears in the transcript; two famigo "read `.cursor/PROJECT.md` first" steps credited by a "commit and push it" turn that edited that file and never read it; a global Decision Memory rule credited by a research document that *described* its template in a sentence, with the mandatory `**Rejected:**` field appearing zero times; and a `/prd-to-plan` command file credited by the session editing a *second copy* of that very document, which `exclude_path` cannot recognise because it compares paths. The principle is one sentence: **a filename lifted out of prose carries no direction.** By the time the token meets a path the run touched, the sentence that made it a target, a warning or an example is gone, and inside a running procedure the invocation is what supplies it back - the step's own file being touched is the step being carried out. A plain rule document supplies nothing, so the honest answer is that the rule is uncompiled and `/compile-rules` is the mechanism for it: a reviewed compiled check is the only path that can credit such a rule, and the only one that can also report a violation of it. The two predicates are therefore not even *derived* for a non-executable document, exactly as the read join is not: a predicate that can never fire would still put a row in the evidence list denying a write that did happen. Measured over the eight snapshot sessions the gate costs eight greens the ground truth calls `used` and removes one it does not - the corpus holds none of the six audited sessions, so it shows the cost side of the trade and not the benefit.

   **`command-echo` is deliberately *not* gated**, on any document. It matches a verb the run executed rather than a noun a sentence mentions, so the direction problem above does not arise: a rule that spells out `yarn type-check && yarn lint && yarn test` is followed by running one of them, whoever wrote the document. It is what correctly credits the famigo quality gate on a plain project `CLAUDE.md`. Dropping it for rule documents too was measured rather than assumed: over the corpus it would cost one further green the truth calls `used`, and off-corpus it turns the famigo quality gate from `used` into `possibly-referenced` - a real signal for no false green removed.

   **A path a block names has to be a file.** A directory (`docs/skills/`, `mobile/services/`, `app/src/`), a slash command (`/create-pr`) and a heading token are all rejected by `_named_paths`, which requires the final component to carry an extension or be a known dotfile: a directory is where work happens rather than something a rule points at, so joining one let any write beneath it stand as proof the rule was followed - the mechanism behind most of the audited false greens. A path inside a *quoted* sentence is excluded too (`_quoted_spans`, the quotation half of `_example_spans` - the inline-code half cannot be used here, since every path a block names is backticked): one skill step whose whole content is "ask the user whether it belongs in `backend/AGENT.md`" was credited in every session that touched that file. The join itself then requires the two final components to be **equal**, and the directories above them have to match as a run sitting **directly** above the filename, tested in **either** direction (`src/index.ts` does not meet `src/components/index.ts`), because either side can be the partial one: the block's side is often relative (`docs/decisions/DECISIONS.md`, which would resolve against this process's cwd), and a shell-written path is routinely `$M/ERRORS.md`, whose unresolvable segments `_path_components` drops - a bare filename on either side leaves no directory to contradict the other. The written side reads the python-heredoc write shapes too (`_python_write_targets`: a tracked `pathlib.Path(...)` binding whose `.write_text` runs, or `open(..., 'w')`), because whole sessions edit markdown through `python3 - <<'PY'` rather than the Edit tool - read only where the heredoc's own line invokes python, or the python example inside a `cat > README.md <<'EOF'` would count as a write; that body stays out of `written_chunks`, since the script is a program and not the document it rewrote. Command echo reads **every** fence, not only shell-tagged ones - the tag requirement exists to stop `import re` being read as a program, and a candidate that must then have run verbatim cannot make that mistake, which is what the palletizer `AGENTS.md` anchor needs with its `just` recipes in a bare fence.

   **"Ran verbatim" means it was a command, not a string** (`_command_echo_count`, `_command_segments`). A Bash call is split into the commands it actually runs - heredoc bodies dropped, quoted arguments masked, then split on `&&`, `||`, `;` and `&` - and the block's command has to match a segment from its **start**. Matching anywhere in the call read a `just talos-hmi-lint` typed into a `gh pr create` PR body as a lint run, which is a description of work counted as the work. The right bound is unchanged (`yarn test` counts `yarn test --watch=false`, never `yarn testing`), and a leading `VAR=value` assignment is stepped over because `CI=1 yarn test` runs `yarn test`. **Single-word fenced commands are echo candidates under that same rule**: `pytest` alone in a fence is as prescribed as `yarn test`, and while echo demanded a space, 18 real `pytest` runs credited the block that prescribes them with nothing. The whole-segment rule is what makes a bare word safe - it has to be the program a segment runs, not a word sitting in another command's arguments. **Multi-token inline-code spans are echo candidates too** (`_inline_commands`): a reband `AGENTS.md` prescribed `npm run typecheck`, `npm run lint` and `npm test` in inline backticks, all three ran verbatim, and the block read `dormant` with the reason "the rule didn't apply" because echo read fences only. A span qualifies under the fence shape test (split on `&&`/`||`/`;`, no quoting, first word not in `NON_CMDS`) and must contain a space; table cells and quoted sentences are excluded, and a single inline word stays the weak tier's, since it is far more often an identifier than a prescription. **In a skill or command, an inline command counts only while that document is the procedure running** (`_procedure_bash`): a window opens at each invocation of the document and closes at the next invocation of a different one. A step's inline command is usually a generic tool (`git status`, `git branch --show-current`), and in one audited session the commit skill's Step 3 read `used` on a branch check that ran for the user's own checkout request before `/commit`, and again under `/create-pr` after it. A fence and a plain rule document stay unwindowed: a rule document has no procedure to run. Like fenced echo it is not direction-aware: a rule that names a command in order to forbid it is credited when that command runs, and a rule demanding one command *before* another is credited whichever order they ran in - the compiled check is what can tell those apart, and a reviewed violation still outranks it.

   **A pipe is not a split point, on either side** (`_fenced_commands`, `_command_segments(keep_pipes=)`). `&&`, `||` and `;` join commands that each stand on their own, so each is separately prescribed; a pipe composes a *single* command out of stages, so a downstream stage is not itself a prescription. Splitting one made `pbcopy` the prescribed command of a rule reading "always pipe through `printf '%s' "..."` - never `echo`", and the exact shape the rule forbids, `echo "x" | pbcopy`, then scored it `used` in green on a real session. A documented pipeline is now kept whole and matched against a pipe-preserving segment of the run (`_normalize_pipeline` spaces both sides identically), and the shape test admits a pipeline but still admits no quoting - so the clipboard rule's own example, whose arguments are quoted, yields no candidate at all. That is the honest outcome rather than a gap: the run's quoted arguments are masked before matching and could never have been compared to it.

   **Command-mention extraction is shape-first, and fences are read separately.** Inline spans go through `_looks_like_command_word`: lower-case, `-` rather than `_`, no trailing separator, at least four characters, and not in `NON_CMDS` (English prose, the nouns every technical document uses for a field or a value, common data-format names, shell keywords). Markdown table rows are excluded first (`_strip_table_rows`): a cell is data, and one column of the retired gh-account table held the repo names `figma` and `formic`, both harvested as programs, so every bash line naming the repo looked like a hit on a rule about GitHub accounts. `_named_paths` still reads tables, because a rule really can put the file it governs in one. `NON_CMDS` no longer carries the entries that were only ever this tool's own vocabulary (`argparse`, `claude.md`, its verdict statuses) - a list curated against one repo's documents grows by an entry per false positive and says nothing about the next user's rules. It is still English, knowingly: deriving stopwords from the user's own corpus belongs to the lexical tier, and this tier can only ever reach `possibly-referenced`, so a leftover false positive claims the block was referenced and can never accuse it. A wordlist alone cannot keep up with a dense technical document - the Architecture block put 167 inline spans through here, nearly all identifiers - and the four-character floor costs the weak tier `gh`, `git` and `jq`, which is the right trade: a command mention can never reach a hard verdict, so all a short false positive can do is claim the block was referenced when nothing tied it to the run. Shell-fenced blocks are read by `_fenced_commands`, which keeps the **whole** command (`yarn type-check`, split on `&&`/`|`/`;`, with an inline `# comment` stripped) and applies neither filter to the first word, because a fence line's first word is a command by position. Before this the fence body was scanned as one inline span, so its language tag `bash` became "the command the rule is about" while the famigo quality gate's 21 real `yarn type-check` runs stayed invisible. For the weak tier only an explicitly shell-tagged fence counts (`_extract_fenced_commands`), and only its single-word commands: a multi-token command belongs to `command-echo` above, so the same command never occupies two evidence rows at two strengths. A single-word fenced command now reaches both tiers, and the mention stands down wherever echo credited the same command - or a whole command starting with it, so inline `yarn test` running silences the weak `yarn` row - on the same trace: a strong row and a weak row about one run read as two facts. **A mention counts only where the word is the program a command segment runs** (`_runs_as_program`, over the same `_command_segments` echo reads, so heredoc bodies and quoted arguments never count). A word anywhere in the call used to be enough, and the cards then read "`null` ran 38×" off `> /dev/null`, "`main` ran 8×" off a branch name and "`plan` ran 1×" off an `mv` argument. A `pytest` that only appears inside `grep -rn pytest tests/` is therefore no mention at all. Where echo found nothing the mention survives, because "this program ran as a command" is exactly what it claims and no more: `yarn add` running is a mention of a rule naming `yarn test`.

   **The lexical tier is a separate module, and its vocabulary is weighted before anything is counted** (`lexical.py`). It replaces the rule that took a block's first eight five-plus-letter words and looked for them anywhere in the assistant's text - the rule that scored a tech-stack table 5/8 against an unrelated discussion of the Effect library, because "Framework", "React", "Native" and "TypeScript" are what a React Native repo says all day. No threshold fixes that; the terms have to change. Three backgrounds weight every candidate term, all computed offline and all **session-wide**, so a block's term set is identical in every turn and cannot drift between the turns a status is combined from and the aggregate it is combined into: **D1** block-collection IDF in Lucene's non-negative form (textbook RSJ IDF goes negative above df 50%, which is exactly where the boilerplate lives), **D2** general English from the baked Zipf list in `data/wordfreq-en.json` (zipf ≥ 5 weights zero, 3.0-5.0 ramps), and **D3** the fraction of the session's own assistant segments carrying the term (≥ 0.35 weights zero). D2 is optional: absent, the tier runs on D1 × D3, which is what keeps the core language-neutral. Each background stands down when it has no sample - fewer than 20 blocks in the collection, fewer than 8 assistant segments, fewer than 3 occurrences of the term - because a background computed from nothing would push blocks toward `not-lexically-scorable`, and an optional signal must never make a label worse.

   `K(block)` is the top 12 surviving terms, unigrams and bigrams (a rule's identity usually lives in a phrase; trigrams would add a third n-gram index over every block of every loaded file for nothing a bigram misses). **Fewer than 3 distinctive terms and the block is `not-lexically-scorable`** - counted over distinct *words*, not term slots, because one distinctive word fills three slots through the phrases it sits in. That is the honest verdict for a table of column headers, and it is not a claim that the block went unused. Scoring is then BM25 coverage (k1 0.9, b 0.75, the length scaled against the session's own average segment length rather than a guessed constant, or the aggregate is penalised for being an aggregate) plus Dunning's G² per term against the higher of the English rate and the loaded documents' rate, with the ≥ 2 observation guard. `topical-overlap` needs all three conditions - ≥ 2 terms at G² ≥ 6.63, coverage ≥ 0.30, and ≥ 1 term at zipf < 4 - because each alone is satisfiable by coincidence. The quote detector is the only path near "strong": a verbatim run of ≥ 8 tokens **and** ≥ 40 characters containing a distinctive term, found with `difflib.SequenceMatcher(autojunk=False)` - the default junk heuristic discards exactly the frequent function words that hold a quoted sentence together - or 5-word shingle containment ≥ 0.15 with ≥ 3 distinctive shingles. Containment, not Jaccard: the two sides are wildly different lengths.

   **Every threshold here is frozen against a labelled set, not chosen** (`tests/fixtures/lexical_pairs.json`, 250 (block, session) pairs; scorer and labelling procedure in `tests/lexical_fixture.py`; gate in `tests/test_calibration.py`). The gate is precision ≥ 0.90 and it fails if `lexical.py` and the fixture disagree about a number, because a threshold is the one thing here a plausible-sounding edit can loosen with nothing going red. Two of the numbers differ from the research doc's recommendation and §3.2 records the sweep behind each: the two run-length bars are an **AND** (the comment on `RUN_TOKENS` in `lexical.py` says why); and the per-term G² bar stays at 6.63 rather than the 15.13 suggested for multiple testing, which removed no false positive and cost a real one. Recall at the frozen point is 0.5, and the misses are in the fixture with a note each - mostly compliance that happened in file writes and verbatim command runs, which is what the structural predicates rather than the vocabulary are for.

   **The query text is assistant prose and nothing else** (`clean_query_segments`). Tool inputs and tool results never enter it, fenced and inline code is stripped, and any whole line that also appears in a tool result is dropped: a Read'd file's content inside the query makes every block of that file match itself, which is the most likely new false positive in the whole tier. **The block side is stripped the same way** (`block_tokens`) - the gh-account rule's whole vocabulary is backticked account and repo names, so keeping code on the block side and stripping it on the query side made its terms unmatchable and the block a guaranteed `no-lexical-trace`, a measurement dressed up as a finding. Tokens are Unicode letters rather than ASCII, so a rule document in another language is scored on its own terms (D2 simply does not know its words, which weights them as the rare terms they are); the four-character token floor is the one place the tier is still Latin-script. Extended thinking stays out too - Phase 5's rule, unchanged: its availability is mixed per model and CLI version, and a signal a transcript may or may not carry must not decide a status, whether it would make the answer better or worse.
7. **Moment assembly** (`assemble_moments` and the family of `_moments_for_*` functions) - given a block and the trace, constructs the chronological "How the agent ended up here" cards (TRIGGER → INTENT → ACTION → OUTCOME). Each predicate type has its own moment-builder, the structural kinds included (`_moments_for_structural`): a block lifted by a write or a verbatim command run otherwise fell through to the loose-keyword cards, putting a topical-overlap narrative under a badge earned by something else entirely.

    **A card is a causal claim, so the causal kinds are gated on the evidence tier.** TRIGGER → INTENT → ACTION reads as "the block caused this", and lexical overlap cannot support it: a Figma design-system block narrated itself with a rate-limiting review because both contain "design", and a tech-stack table with an Effect-vs-react-query discussion because both contain "React". Two non-causal kinds carry that weight instead, each disclaiming causation *in its own card text* (`CO_OCCURRENCE_NOTE` / `THINKING_SELF_REPORT_NOTE`) rather than trusting the reader to know which kinds are weak. `co-occurrence` is what a block gets when the only evidence is shared wording - `_moments_for_lexical` returns exactly one such card and `assemble_moments` returns it untouched, because a second card there starts reassembling the narrative - and it is also what a bare command mention gets (`_moments_for_command_mention`), still citing the run count and the command verbatim, and what a bare `/name` in the prompt gets in `_moments_for_skill_or_command`, since `skill-invocation` refuses a mention as evidence the skill ran and a ✓ TRIGGER there put a green step above the weaker badge that refusal earns. `corroboration` is readable extended thinking, below.

    **The card and the badge read one lexical result** (`_lexical_result`, memoised per block content on the trace): `assess_block` tokenized the block one way for the `unused` / `possibly-referenced` split and the card builder another, so a block could sit `unused` - "no keyword overlap with the assistant's reasoning" - above a card counting three shared words. Both read the one record now, and the CLI prints each moment's `kind` (`_moment_line`) because the kind is what carries the epistemic weight and the page shows it as a chip.

    **The INTENT slot takes structural antecedents only** (`_structural_intents`): the `Read` that delivered the file, or the agent's narration immediately before it. It used to take whichever assistant paragraph scored highest on the block's keywords, which is how Decision Memory ended up narrated by YIN pitch-detection math. Nothing ranks prose by keyword overlap any more: the one remaining caller, duplicate classification, reads each block's own verdict and lexical label instead (step 10).

    **Thinking text is read, and its absence costs nothing** (`_thinking_corroboration`, and `chronological_segments` no longer hardcodes it empty). Availability is mixed per model and CLI version: officially the field is encrypted and empty, empirically 43 of 82 blocks were readable in a recent famigo transcript, so both shapes arrive and the encrypted-gap card in `_moments_for_read_driven` counts only the unreadable ones. The join is on `_thinking_join_tokens` - the skill's own `/name`, the paths the block names, the whole commands it spells out - never on the block's prose terms: prose overlap matched an `/implement-plan` pointer on the words "agent" and "review" in this repo's own logs. Thinking is deliberately absent from `assistant_text_segments`, so it can never reach `all_assistant_text` and move a keyword verdict; measured faithfulness is under 20%, and a signal a transcript may or may not carry must not decide a status.
8. **Verdict** (`assess_block`) - combines predicates and moments into a judgment with cited evidence, over a **7-status taxonomy** split into two families:

    - USED: `used`, `used-partial`, `possibly-referenced`, `ignored`
    - NOT-USED: `undelivered`, `unused`, `dormant`, `not-loaded`

    Evidence comes in **two tiers**, and the tier caps the verdict. **Strong** evidence ties the block to a specific observable outcome: a trigger whose command the run really invoked (`trigger`), one of the structural joins from step 6 (`skill-invocation`, `reads-named-path`, `writes-to-named-path`, `template-echo`, `command-echo` - each a record of what the run did, tied to something the block itself names), or a reviewed compiled check that ran (step 8b). Every one of those is either a harness record or a human-reviewed check, so a rule worded differently - or written in another language - is judged the same way. Only strong predicates can produce `used`, `used-partial` or `ignored` - and since step 6 retired the prose predicates, **no predicate can produce `ignored` at all**: every surviving strong kind is either satisfied exactly when it is applicable (a trigger, which is applicable only where an invocation record exists) or credit-only (`matches` unconditionally true). A red badge now comes only from step 8b, which refuses to report one without a file, a line and the matched text, so every accusation carries a citation by construction (`tests/test_generalization.py::test_only_a_compiled_check_can_call_a_rule_violated`). `used-partial` survives at session scope, from the combine. **Weak** evidence only observes that something the block happens to name occurred, with no causal link back to the block: a bare `command-mention` (whose `matches` is unconditionally true) or the lexical tier of step 6. Weak evidence tops out at `possibly-referenced`; it never reaches green. A block with predicates but nothing applicable stays `dormant`.

    **The lexical tier is consulted only when nothing else has anything to say**, and what it reports is baked as `evidenceLabel` (one of `echoed`, `topical-overlap`, `no-lexical-trace`, `not-lexically-scorable`) plus the `lexical` record behind it. Both keys are appended and appear only where the tier actually ran: a block decided by a Skill call or a compiled check has no lexical claim to make, and inventing a label for it would read as one. **The label names the evidence, never the mechanism, and never a cause.** `echoed` and `topical-overlap` map to `possibly-referenced`; `no-lexical-trace` and `not-lexically-scorable` map to `unused` - but neither is evidence the block was ignored. Silent behavioural compliance leaves no lexical trace at all, and a block with fewer than three distinctive terms was never scored in the first place; the reason line says so in both cases. Unlike `status`, the label is **not** recombined from the turns at aggregate scope: it is a measurement of a scope's prose rather than a verdict about it, and the aggregate's prose is genuinely the whole session, so measuring it directly is the honest answer where combining would not be. `_is_strong` / `_fired_strongly` are the shared helpers, and `_fired_strongly` insists on strength **and** `applicable` **and** `matches` together: `matches` alone is true for every command mention.

    Applicability and **exercise** are separate questions. Applicability asks whether the rule's precondition was met; exercise asks whether the run did the kind of thing the rule is about. They part company for a cwd-conditional rule: without the distinction a turn that ran no `gh` command at all was reported as a GitHub-account violation, which is how a dozen compliant turns ended up under a red session badge. The question now lives in `rule_checks`, which answers it from the corpus rather than from prose - `_antecedent` / `_in_scope`, and the `not-exercised` block state (step 8b). On the predicate side the contract survives as `_is_exercised` plus the optional `exercised(trace)` callable, and **no current kind supplies one**: the retired `path-table` was the only predicate whose precondition (the cwd) could be met without the rule being exercised, and every remaining kind's precondition *is* its exercise (a trigger that was typed, a file that was written, a command that ran).

    `combine_verdicts` ranks the statuses `used` > `used-partial` > `possibly-referenced` > the NOT-USED family, so the invariant "used in any turn -> used at session scope" still holds and weak evidence can never outrank real evidence. `ignored` is the exception to a plain ranking: it wins over the NOT-USED family, but a scope with **both** `ignored` and `used`/`used-partial` turns combines to `used-partial`. One mis-scored turn used to repaint a session over a dozen provably compliant ones, and `ignored` at session scope has to mean what it says - the rule applied and was satisfied nowhere. The downgrade hides nothing: `used-partial` is not green, the violating turn stays red at turn scope, and the aggregate's reason counts the turns. Every `ignored` reaching the combine is exercised by construction, because `assess_block` refuses to say `ignored` without exercise.

    **`contested` is a third thing shown beside the badge, and it is not a status** (`CONTESTABLE_STATUSES`, `_contested_from`). The blind-judge experiment measured a judge that is better than the code at noticing a rule *was* followed (28 missed compliances against the code's 84) and far worse at not inventing compliance that never happened (53 false greens against 2), so a judge answer informs a reader and may never award a badge. The two tiers disagree on 43.4% of blocks, which is why only one direction is reported: a block whose status is `unused` or `dormant`, which the judge answered `compliant`, having quoted something `_quote_span` located in the evidence it was handed (`judgeQuote`, set only where the quote resolved - a candidate finding's `match` is the span *this tool* enumerated and is there whether the model cited anything or not). A judge `violated` contests nothing in either direction: that is where its eleven false reds live, and the code's red path already requires a citation by construction. The record is `{judgeVerdict, quote, reason}`, appended only where there is one, and it never reaches `combine_verdicts` - where the combine lifts an aggregate block out of the NOT-USED family the flag is dropped, or "the judge read this as used" would sit beside a verdict that already says so. `contestedBlocks` is the count, baked at both scopes off the final payload. Over the frozen corpus the ceiling is 18 of 11,991 blocks (0.2%), because only a document with a record parked for the judge is ever asked a semantic question at all.

    The aggregate's reason is regenerated from the combined status (`combined_reason`) wherever the combine rule overrules the aggregate's own assessment. The two were computed independently, so one real record read status `ignored` above the reason "1 predicate(s) applied and were satisfied" - three realities in one row. Moments and evidence keep their session-wide assessment, which is still the most informative view at aggregate scope.

    Delivery is checked before predicates run: `_delivery_range` records `delivered_ranges` as a list of merged intervals (`delivered_from` / `delivered_to` are only its outer bounds), so a file read as two disjoint ranges marks blocks in the gap `undelivered` instead of scoring text the model never saw.
8b. **Rule checks** (`rule_checks.py`, wired in through `assess_block` -> `_rule_check_for` / `_apply_rule_check`) - the only mechanism that may call a rule *violated*. See "Rule checks" below. Each block may carry a `ruleCheck` record; a confirmed violation from a reviewed checks file (confidence `high` or `medium`) is what turns a block `ignored`, citing file, line and matched text in the reason.

    **A compiled check also gives credit, and only from its satisfied stage.** A conditional kind whose antecedent fired and whose consequent happened (`stage == satisfied`, from a checks file, medium or high confidence) lifts the block to `used`, and a `not-exercised` record folds an `unused` block to `dormant` - which is what `dormant` says - and gives an already-`dormant` block its own reason in place of the generic "no predicate's preconditions were met". A satisfied check still draws its compliance card under a block a prescribed command already lifted to `used`, without rewriting that block's reason. Both exist because step 6 no longer derives a strong predicate from prose: without them a session that obeyed a compiled rule a dozen times read `unused`, and one violating turn then repainted the whole session `ignored` at the combine, which is F-COMBINE coming back through the new mechanism. The credit is deliberately narrower than `clear`: `clear` also covers "the checks matched nothing", which for a forbidden-pattern rule over a coarse scope (any bash command at all, for a shell kind) is the absence of a violation rather than evidence the block was followed. A `fallback` (mechanically extracted) record gives neither credit nor blame, exactly as before.
9. **Token attribution** (`attribute_request`, `attribute_usage`, `block_costs`, `history_chars_by_request`, `_annotate_costs`) - splits each request's reported prompt tokens across the context items that were resident for it, proportionally by character size, plus a remainder bucket sized by the conversation prefix so file figures aren't inflated by chat growth. Rolled up per file into `cost` (`sentCount`, `tokens`, `cached`, `fresh`): the same file is resent on every request, which is where the real money goes. The cached/fresh split comes from the request's own figures. A file accrues only while it is resident (`resident_turns`): from the first turn that loaded it until a compaction evicts it, lifted onto requests by event index (`_nonresident_by_request`). The aggregate is re-priced once the turns are known, because its own first pass charged a skill invoked in turn 9 for the eight turns before it was in context. Rounding uses the largest-remainder method so the parts always sum back to `usage`'s `promptTokens` exactly. Per-block figures (`block_costs`) divide a file's cost by line share and always carry `estimated: true` - the UI must label them.
10. **Duplicate detection** (`compute_duplicates`, `_classify_pair`) - n-gram shingle containment across all loaded context files, classified as `redundant` / `overlap` / `related`. `_classify_pair` re-judges nothing: a pair is `referenced` when either block's baked status is `used` / `used-partial` or its lexical label is `echoed` / `topical-overlap` (the topic was live this session), so a pair carrying nothing but bare command mentions is honestly `redundant`. A second matcher here once let a pair read `referenced` above two blocks that both read `unused`. Pair costs come from step 9, not from character counts: `tokensA` / `tokensB` are each block's attributed cost across every request that carried it, and `tokens` is the overlapping share of the cheaper side (the part that could have been deleted). A pair involving a file that was never sent costs zero, which is the honest answer.
11. **Timeline + file activity** (`build_timeline`, `file_activity`).
11b. **Per-file rollup** (`_annotate_activity`, `_annotate_rollup`, `_violation_headline`) - what the drill-down's File and Turn levels read. Each context-file record gains `activity` (`reads` / `edits` in this scope) and `rollup` (`statusCounts`, `active`, `summary`); each turn record and each `data.sessions[]` entry gains a `headline`. `activity` joins the raw absolute `file_path` a tool input carried to a context file's `abs_path` by resolving **both** sides (`_resolve_key`): the display path is the tilde form, and an unresolved join reports every file as untouched, which looks plausible. A file is `active` when it was read or edited in the scope or any of its blocks has a status in `ACTIVE_BLOCK_STATUSES`; everything else, `not-loaded` included, is quiet. `summary` is first-match, so it names the most consequential thing that happened rather than a generic tally. `process_session` re-runs `_annotate_rollup` over the aggregate after the per-turn status-combination patch, or the aggregate's file summary would contradict the block list beneath it.
11c. **Wasted context** (`task_digest`, `_file_relevance_summary`, `judge_relevance`, `wasted_context`, `_waste_rollup`) - what each loaded file cost, how many turns it was resident (`resident_turns`, never merely listed) - the same residency a turn's loading reads for an invoked skill or command (step 5), so a file cannot be billed for a turn that reports it `not-loaded`, and (unless `--no-judge`) whether it pertained to the session at all. Baked at **session scope only**, like `ruleCompile`: the question is what the *session* did, and a per-turn answer would both multiply the calls and answer something nobody asked. `per_session.wastedContext` is `{loadedFiles, asked, notPertinent, tokens, totalTokens, judged, note, files[]}` - the counts every view prints, baked once, so the page cannot tally the same list differently than `--query` does - `per_session.taskDigest` is the question's other half, `summary.wastedContext` is the same object minus `files` (the `ruleCompile` split), and a judged file also carries `relevance` on its own context-file record so the file screen and the waste list read one fact. Ordering is relevance first, cost second, with `None` (nothing asked) ranked beside `undecidable` - an unasked question and an unanswerable one are the same amount of knowledge, and ranking either below a pertinent file would claim the tier said something it did not. With the judge off every row ranks the same, so the list is the cost ordering the offline build always produced. The relevance question has no flag of its own: it runs with the rest of the tier, and being a call per loaded file per session it is the part of a default bake most likely to meet the call budget, which is why it is asked most-expensive-file first. `asked` excludes calls the backend never answered, and a file whose summary tries to instruct the judge is never sent at all. `note` is why nothing was asked when the tier *was* on: a transcript with no real user prompt has no task to be relevant to, and asking anyway would spend a call per file on an empty question and file every such session under one cache entry per file.

12. **Per-session assembly** (`process_session`) runs steps 3–11c once per transcript, producing a `summary` (lightweight, for the picker) and `per_session` (the full data the active view needs).
13. **Session compare** (`compare_sessions`, `align_actions`, `compare_context_files`) - only when `--compare A B` is passed. Reduces each turn to its ordered tool-call names (read back off the baked turn timelines, `turn_actions`), aligns the two sequences with `difflib.SequenceMatcher` (`autojunk=False`, because tool names are exactly the high-frequency tokens autojunk would discard), and emits paired/unpaired steps plus deltas for tool calls, edits, tokens and per-block verdicts. Never align by index: one extra call early on shifts every later index and would report the whole tail as divergent. Turn *rows*, by contrast, do pair by ordinal - a turn is anchored to a human prompt, so turn N is the same instruction on both sides. Context files are diffed block-wise by the stable block IDs; a file whose block content changed is flagged `drifted`. A pair whose first prompts differ is flagged `sameTask: false`, because deltas between different tasks mislead. `build_data` attaches the result under a top-level `compare` key; without the flag the key is absent and the payload is byte-identical to a pre-compare build.
14. **HTML emit** (`main`) - JSON-serializes everything, escapes `</` and `<!--` so it survives the surrounding `<script>` tag, and substitutes it into `HTML_TEMPLATE` (the giant raw string at the bottom of the file). Output is one self-contained file with a vanilla-JS frontend that renders panels from the baked-in JSON.

15. **Query mode** (`cmd_query`, `run_query`) - `--query` stops before step 14: it bakes the same payload (`select_transcripts` + `bake_sessions` + `build_data`, shared verbatim with `main`) and prints plain text instead of writing HTML. It renders only what is already baked, so the CLI and the page can never disagree.

### Where things live in the script

- CLI args: `parse_args`, with `_split_query_argv` just above it.
- HTML/CSS/JS template: the `HTML_TEMPLATE` raw string, from its definition to EOF.
- Multi-session baking is on by default (`--all-sessions`, capped at `--max-sessions 20`). The active session is marked `activeSessionId`.

### The Blocks view is a drill-down

The Blocks view navigates by descending sessions -> turns -> files -> blocks, one level per click, with a breadcrumb and a collapsed ancestor bar per level above the current one. There are no session or turn dropdowns and no file-tree aside; the file list is a level.

- One state object, `nav = {sessionId, turnId, agentId, filePath, blockId}`. **Level is derived from it (`currentLevel()`), never stored.** `navigate(patch)` is the only writer: it merges the patch, nulls every deeper field, syncs `activeSessionId` / `activeTurnId`, rewrites the hash and re-renders.
- `activeTurnId` is **app-wide scope, not the Blocks view's alone**. Timeline, Files and Duplicates all read `activeTurn()`, so navigation that leaves it behind makes those tabs silently show a different turn than the verdict just read.
- A session whose `turnCount` is 1 skips the turn level in both directions: descending into it lands on its file list, and ascending from that list leaves the session.
- A subagent hangs off its turn **at the same rank as a context file**: `agentId` is a peer of `filePath`, not a level below it, which is why it is not in `NAV_KEYS` (the ranked walk cannot express two fields at one rank, so each of the two clears the other explicitly). `currentLevel()` returns `'agent'` when it is set, and the agent screen replaces the file list at its level rather than the whole layout, so the breadcrumb, ancestor bars and scope badge stay put. Both of an agent's tiles - the send-off and the report-back - carry the identical patch `{turnId: <spawn turn>, agentId}`: seeing the two as one run is the point. Escape from the agent screen goes back to the turns list, which is the only place it can be opened from.
- The hash is `#s=&t=&a=&f=&b=`, written with `replaceState` (`pushState` would make the back button walk the descent one row at a time) and re-read at boot. `a=` and `f=` are peers and are never both written, so `navFromHash` resolves the agent first and returns. Parsing never throws: each level resolves against the baked data or the walk stops there, because a blank pane leaves the reader no way back. `navFromHash` adds the `agentId` key to the path **only when it resolves** - a patch merely *containing* `agentId` clears `filePath` and `blockId`, so returning a null one would strip every file deep link on boot.
- Files and blocks render in an Active group above a Quiet one, from the baked `rollup.active` and the `ACTIVE_STATUSES` mirror of `ACTIVE_BLOCK_STATUSES`. Both are always rendered; it is a classification, not a filter.

### Rule checks (`rule_checks.py`)

**The tool never calls a model and never makes a network request.** A prose rule is interpreted exactly once, *outside* this tool, at authoring time.

**Compile step (`/compile-rules`, outside the tool).** [`.claude/commands/compile-rules.md`](.claude/commands/compile-rules.md) is the slash command; [`prompts/translate-rules.md`](prompts/translate-rules.md) is the authoritative flow it follows, and the command deliberately points at the prompt rather than restating it. The flow extracts every rule as its own record, classifies it into a bucket, generates patterns plus fixtures plus both example lists, verifies them, writes `<doc>.checks.json` beside the document (e.g. `CLAUDE.md.checks.json`; `<stem>.checks.json` also resolves), and then **stops at a review gate**: it names the file and the per-bucket counts and does not commit it. That file is a reviewable repo artifact whose patterns run as written on every later audit - read it before trusting it. Expect it to refuse most rules (research doc §3.1 has the measured rate); that refusal rate is the design working, not a failure.

A statement the prompt makes about the corpus, the vocabulary or the loader's gates is part of the contract: `tests/test_compile_flow.py` asserts the prompt names every v2 field and closed-set value the loader enforces, because a prompt that omits one compiles a record that is refused at load and nothing at check time can say the prompt was the cause.

**The first audit is the onboarding step** (`_rule_compile_rollup`, `rule_checks.compile_state` / `compile_status`). A rule with no reviewed record reports `not-checkable`, which reads as a limit of the tool when the truth is that nobody has compiled it yet - so every report counts the project's rule documents and names the command. `compile_state` decides one rule's state - `compiled`, `stale`, `refused`, `uncompiled` - and **both the session-wide counts and each block's `ruleCheck.hint` read it**, or a document reported fully compiled could sit above a block asking the reader to compile that very rule. `refused` is an answer the compiler gave and this tool can report (an explicit `not_checkable`, or a bucket parked for the judge tier), so it carries no hint; a record that did not survive the loader (stale, demoted, rejected) is `uncompiled`, because re-compiling is the fix. The rollup is baked from the aggregate payload only (`summary.ruleCompile` carries the counts and the hint, `per_session.ruleCompile` adds the per-document breakdown): the documents on disk are a property of the project, not of a turn. The analysis side never runs the compiler, so the offline guarantee is untouched.

**The onboarding line counts documents, and the breakdown names the bucket mix.** The hint says how many rule *documents* are uncompiled rather than how many rules are: the reader's next action is to run the command once per document, and a rule count tells them how much prose is unchecked instead of how much work is in front of them. Beside the four compile states each document reports its mix - `deterministic`, `judged`, `notCheckable` (`rule_checks.COMPILE_BUCKETS`, counted per rule-stating block the way the states are) - and one `state` of its own (`rule_checks.document_state`). `compiled` is reachable only with nothing left to compile **and** at least one rule this tool can decide offline, so a document whose every record was parked for the judge reports `refused`: reading "compiled" as "decidable" is exactly the mistake the mix exists to prevent. `python3 build_real_view.py --query sessions --compile-status` prints the whole project on one screen - every rule document, its state, its mix, its checks file, and the command that compiles the next one - and reads the same baked `ruleCompile` the page and the session screen do. **Its scope is the project, not the session** (`project_rule_documents`, walked once per project and cached): the loaded documents come first and a disk walk adds the rest, because a nested `backend/CLAUDE.md` is delivered only where the harness injected it or something read it - and a reader who sees every listed document compiled must not still have uncompiled rules one directory down. A document git ignores is left out (`_git_ignored`, one `git check-ignore` call, and nothing excluded where git cannot answer): a frozen transcript corpus or a vendored checkout under the project is input data, and this repo's own gitignored `snapshots/` tree alone would otherwise report 32 other projects' documents as work to do.

**The worked example.** [`docs/example-CLAUDE.md.checks.json`](docs/example-CLAUDE.md.checks.json) is the first checks file this tool ever compiled, rewritten away from the project it came from - every heading, rule sentence, statement, message and refusal reason is this repo's own wording for a fictional monorepo, because renaming the packages would leave that project's sentences and operational detail in the prose fields, which is the content the privacy line is about. 46 prose rules became 17 deterministic checks, 9 parked for the judge and 20 honestly refused, with nothing rejected or demoted at the loader gate. The refusal rate is the design working, which is why the example ships with its `not_checkable` list intact rather than only its checks. `rule_key` is dropped from every record there, because a key pins a check to the exact rule text it was compiled from and beside no document it would only ever read as stale. `tests/test_compile_flow.py` re-runs the loader over it, so an example that would be refused cannot ship.

Which blocks count as rules is `_looks_like_a_rule` / `RULE_CUE_RE`, and its cue set has to be a superset of every cue an accusing or typing mechanism reads: the mechanical fallback's `NEGATION_RE`, and `classify_block`'s `Rule:` label. A self-labelled `**Rule:**` block that the counts did not see was a rule nobody was ever told to compile - which is exactly what the gh-account block became the moment its bespoke predicate was retired, reporting nothing at all. (The cue set is English, and moving rule-cue detection to authoring time is §4 item 3 of the research doc; being wrong here costs a missing hint, never a verdict.)

**Checks-file format.** `{"source", "checks": [...], "not_checkable": [...]}`. Each check carries `id`, `rule_ref` (the heading it belongs to, or a line number), `rule_text`, `domain` (`source` | `shell` | `path` | `tool`), `kind` from the closed vocabulary in `rule_checks.VOCABULARY`, its pattern fields, `applies_to` globs, `confidence`, `message`, and a mandatory `self_test` with both `should_match` and `should_not_match` (`fixtures` is the v2 name for the same object). An optional `rule_key` (from `rule_checks.rule_key(heading, text)`) pins the check to the exact rule text it was written for: if the rule is edited the key stops matching and the check is skipped as stale rather than applied to wording it never read.

**Record format v2** (research doc §8). Every v2 field is optional, so a v1 checks file loads and reports exactly what it always did - the fields say what a record *is*, and a file that says nothing is read the way it was. A record may declare `statement` (the rule as one testable question), `scope` (`code` | `communication` | `process`), `evidence` (`diff` | `files` | `transcript`), `bucket` (`deterministic` | `hybrid` | `judged`), and `examples_positive` / `examples_negative`. A value outside its closed set is refused rather than ignored, and so is an `evidence` the kind cannot read (a source pattern over the tool log, a tool pattern over a file's text): a check reading nothing reports as a rule nothing triggered, which looks like honest silence instead of a broken record.

**Buckets, and what a failing fixture does.** `deterministic` is the only bucket this tool can decide *offline*. `hybrid` (sites enumerated here, each judged in isolation) and `judged` are parked in `loaded["judged"]`, applied to nothing, and reported on the block as unchecked with the bucket named - a rule nobody could check must never render as one that was followed. A default run answers them instead; see "The judge tier" below. A **deterministic record whose fixtures fail to reproduce here is demoted to `judged` and says so** (`loaded["demoted"]`, carrying `fromBucket`): the point of re-running fixtures is that a broken check becomes visible as a broken check, so a silent drop would defeat it. A record with no `bucket` field is a v1 record and is still *refused* on a fixture failure - taking the demotion path for it would change what every existing checks file reports about itself. Both lists ride on the block's `ruleCheck` as `demoted` / `judged`, beside `stale`, and both the page and `--query` name them: "its fixtures are broken", "no judge ran it" and "this rule cannot be expressed" are three different facts, and a reader who cannot tell them apart cannot tell which one to fix.

**Evidence scoping: the net diff, not every hunk.** `build_corpus` returns `final_code` beside `code` - the same paths after every write is replayed against the others (`_net_code`, `_apply_edit`), so an `old_string` the buffer already holds is *substituted* rather than appended and a revert reads as a revert. Source and candidate kinds read that net diff by default, v1 checks included (`_source_entries`): a rule about code is a rule about the code that ended up in the tree, and 3-19% of what the eight baseline sessions wrote never survived to it - text a check scanning `code` could have accused the agent over, in a file where the reader would go looking and not find it. `evidence: "files"` opts back into every hunk, for the rare rule about what was written at all. Heredoc bodies a Bash call wrote into a file reach both views through `build_corpus(shell_writes=)`, and the edit-tool hunks through `written_texts`, the one switch over the edit tools that `build_real_view`'s structural joins read too. `_in_scope` reads the same corpus the check does, or an empty net diff would report `clear`.

**Omission rules need a candidate search.** A rule like "always implement the catch body" is broken by writing *nothing*, so the pattern that would catch it is absent by definition - the external spec calls a missing candidate search the most common source of a false "all clear". `enumerate_candidates(kind, entries, globs)` extracts the sites instead, from `CANDIDATE_KINDS` (`catch_block`, `comment`), each carrying path, line, the text to quote and its own body separately. `catch_block` reads the comment-stripped view, so a commented-out `catch` is not a site and a comment-only body reads as the empty body it is; `comment` derives its spans from the same central stripper (via a sentinel fill) rather than re-parsing, because a second matcher for one question is how block-comment continuation lines were missed the first time, and a file whose extension names no language yields nothing. The `candidate_requires` kind cites any site whose own text fails its pattern; no site at all is `not-exercised`, never `clear`. The strict-vs-stripped agreement rule above does not apply to it and does not need to: the site is extracted from the stripped view, so it cannot itself be inside a comment, and its body is matched stripped because a token that appears only in a comment is not the rule being satisfied. The judge tier asks its question about these same records - one enumeration, or the deterministic half and the judged half disagree about which sites exist.

**The string-literal trap.** Two rule shapes look trivially checkable and are not, because string stripping is unconditional: a rule about an **import path** (`never import another store's singleton`) and a rule about **UI text in code** (`no user-facing copy in code, it goes in the i18n files`). Both live entirely inside string literals, which `strip_comments_and_strings` blanks before any pattern runs, so a character pattern matches nothing and reports `clear` - "the rule was followed" - over a rule nothing looked at. Either the record is `ast_forbidden`, which asks the syntax tree, or the rule goes to `not_checkable`; there is no third answer, and with no ast-grep installed the honest report is `not-checkable` naming the install command. The pilot hit this on three separate rules.

**What load time enforces.**

- **Self-tests are re-run here** with this tool's matcher, and any check that fails is refused and reported as `not-checkable`. The pilot found a check that passed the generator's own verification and failed the consumer's, because the two disagreed about `required_order`; a generator's claim that its tests pass is not evidence. A tool kind's self-test snippet is itself a tool log - one call per line, in order (`_selftest_tools`) - because an ordering check that could not be given a sequence could not be tested at all, which is the one thing this gate exists to catch.
- **Comments and string literals are stripped centrally** (`strip_comments_and_strings`) before any pattern runs, self-test snippets included, preserving offsets so spans and line numbers stay true. Per-pattern comment guards are explicitly *not* the mechanism: a line-anchored guard cannot see the continuation lines of a block comment, which is how the pilot false-positived inside a CSS comment. String stripping is **unconditional** on the source path, template literals included. It used to be a per-check opt-in (`ignore_strings`; the comment beside `strip_comments_and_strings` records the false red that ended it). The field is still accepted, so a checks file written against the old format keeps loading, and it does nothing. The cost is stated where it is paid: a rule genuinely about the *contents* of a string (an import path, a `className`) can no longer be matched by characters and needs the syntax tree, which is what `ast_forbidden` and its backend are for. `strip_strings=False` survives for one caller, `_comment_candidates`, which reads back what the stripper blanked and would otherwise report every string literal as a comment.
- A finding is `violated` only when the strict match and the match over stripped text **agree**; disagreement is `unclear`, never a violation. Every violation carries a citable span (path, line, matched text, check id): a candidate without one is not reportable.
- An inline `ctx-allow` marker (optionally `ctx-allow: <check-id>`) on the match's line or the line above downgrades a finding to `acknowledged`, for the deliberate exception with a documented rationale.

**The governing prompt behind a cited call.** `ctx-allow` lets written code carry a deliberate exception at the violation site; a transcript has no such marker, so "the user typed this action in the prompt that caused the call" - the strongest rationale there is - was invisible to the checker, and the first checks file ever compiled red-badged six real sessions for doing what they were told. Every finding that cites a call (the tool kinds, and `forbidden_command` / `required_command` through the `command_calls` list `build_corpus` returns beside `commands`) therefore carries `governingPrompt` - `{text, turnIndex, callIndex}` - and both the page and `--query` print it verbatim beside the citation. The join is positional and nothing else (`build_real_view.governing_prompts_for_calls`): turns already run prompt to prompt, so the prompt is the one of the turn whose event range **contains** the call, not the nearest earlier prompt by event index - the two differ for a call the agent made before the human first spoke, which a turn absorbs. The turns it reads are the caller's own (`turns=`), the same list the payload splits with - compaction boundaries included: splitting again from the prompts alone numbered every turn after a compaction low, so a finding cited a turn number the drill-down and `--query` contradicted, and a compaction-carved turn, which holds no prompt of its own, reported none at all although the prompt in flight governs it. A turn with no real user prompt carries none, because absence must never read as authorisation. **Deciding authorisation by matching words in the prompt is refused**: it is the single-user prose matching step 6 retired, and it would read a Polish prompt as silence.

**The judged authorisation question** (`rule_checks.authorise_findings`, `judge_tier.authorisation_request`) is the other half, and only with the judge on. One narrow question per finding - *did the user, in this turn, instruct the action this call performs?* - carrying the prompt and the call line and **not the rule**, whose wording cannot help and can only bias. An affirmative answer sets the finding to `acknowledged`, the state that already means "a violation the site deliberately suppresses", and records the judge's reason; a no, an unreadable reply and an unreachable backend all leave the violation standing. Only the deterministic tier's own findings are asked: a judge excusing another judge's accusation is two models agreeing with each other rather than with the evidence. A call line that tries to address the auditor is never asked about at all (`callInjections`, the mirror of the relevance question's `fileInjections`): the call is agent-generated content, removing a red badge is the one direction an attack wants, and the attempt is recorded on the very finding it tried to move rather than passing silently - while a hit in the prompt discards nothing, because that half is the user's own words. This is the one place an absent optional signal leaves an accusation standing, which is deliberate and is why the offline report prints the prompt - `tests/test_degradation.py::test_the_judge_tier_off_never_acknowledges_an_authorised_action` holds the contract from both sides.

**The tool log and the tool kinds.** `build_corpus` returns a fourth shape beside `code` / `commands` / `paths`: `tools`, every call in call order carrying its own `index`, so ordering and counts are decidable. `commands` and `paths` are unordered sets of facts, which is why "check the account before running `gh`" could not be expressed over them at all - and ordering constraints are where most real agent failures sit (research doc §3.3). A call is one **line**, `<ToolName> <arguments>`, and every tool pattern matches that line (`arg_pattern` alone matches the arguments without the name). Two exclusions keep the line honest: written file contents, because a whole file pasted into a line makes every citation it anchors unreadable, and the human-facing `description` a Bash call carries, because it is prose *about* the call (`_PROSE_ARG_FIELDS` in `rule_checks` records the call it condemned).

**A pattern may not span a command join.** `&&`, `||` and `;` join commands that each stand on their own, while a call is rendered as a single line, so an unanchored run like `[^\n]*` reached straight across them: a branch push followed by `gh pr create --base master` was read as `git push ... master` and the run was red-badged for the one action it did not take. A match that would have to cross a join is refused and the next one is tried, in the shell kinds as well as the tool kinds, with quoted arguments masked first so a separator inside a quoted string is not a join. A pipe is deliberately not a join, for the same reason `command-echo` does not split on one: it composes a single command out of stages. Nothing about ordering changes - a prior earlier in the same compound line still counts, because the two matches are compared by offset within the same call.

The kinds are `tool_forbidden`, `tool_required`, `tool_precedes`, `tool_never_without_prior`, `tool_arg_matches`, `tool_call_count` and `writes_to_path`. `tool_required` and `writes_to_path` take a `trigger_pattern` rather than standing alone, and `tool_call_count` refuses to fire when its pattern matched nothing, for the same reason in each case: an obligation that simply never happened has no call to quote, and a violation without a citable span is not reportable. The cited call is always the one that went wrong - the `gh` with no prior check, the call that jumped the queue, the first call past a `max_calls` limit, the trigger whose obligation went unmet.

`tool_required` is deliberately **order-blind** - it asks only whether both things happened. "B after A" belongs to `tool_precedes`, whose antecedent is A alone, so a session that edited and never ran the tests is `consequent-missed`, never `not-exercised`; "A before B" belongs to `tool_never_without_prior`; and "after *every* edit" is not expressible at all and must go to `not_checkable`. The authoring prompt says all three, because the natural mis-encoding produces a green badge over a session that did the two things the wrong way round.

Two things the tool kinds get right only because they were measured against the real anchors. **A prior earlier within the same line counts** for `tool_never_without_prior`: agents write "check, then run" as one compound Bash call (`gh auth status …; gh pr list`), so comparing call indices alone condemned the most compliant shape there is. And **a satisfied or unfired stage note must not spend the finding limit** (`_capped`) - a tool kind reports its stage even when nothing is wrong, so twenty quiet rules on one block would otherwise stop the twenty-first from ever being evaluated and drop the only real violation.

**Two-stage conditional reporting.** Every finding from a *conditional* tool kind carries a `stage`: `antecedent-not-fired`, `consequent-missed` or `satisfied` (`rule_checks.STAGE_*`). `tool_forbidden` carries none, deliberately: the call happening is the whole finding, and labelling it a missed consequent tells the reader an obligation went unmet under a badge that is about an action being taken. Over 30% of real conditional failures are wrong condition-checking rather than a wrong action, so which stage failed *is* the finding, and an antecedent that never fired is a different fact from a consequent that was missed. The unfired one is the only finding with nothing to cite (`line` 0, empty `match`): picking some other call to point at would put a citation under a claim no call supports. `_in_scope` asks each tool check's own `_antecedent`, so the block state agrees with the stage - a rule whose trigger never came up is `not-exercised`, never `clear`, because `clear` reads as "the rule was followed" when the truth is that it was never tested.

**The optional ast-grep backend** (`ast_grep_binary`, `unavailable_reason`, `_evaluate_ast`; installed by `install_ast_grep.py`). One kind, `ast_forbidden`, carries an `ast_pattern` that is code rather than a regex - so `_validate` skips the regex compile for that field and the fixtures are what validate it. It exists because `strip_comments_and_strings` only *approximates* the comment/string question: a regex for an empty catch body accuses one that sits inside a documentation string, and calls a comment-only body `unclear`, because stripping the comment is exactly what empties it. Matching the syntax tree decides both.

Three rules make it an optional enhancer rather than a dependency. **Resolution never searches PATH** - the binary comes from the tool's own `vendor/` directory or from an explicit `CTXIDE_AST_GREP`, and an override that does not resolve returns None rather than falling through to the vendored one, because running a binary the user did not choose hands the verdicts to a program nobody reviewed. **Absent, the check is moved out of `applied` and reported `not-checkable` with the install command**, never approximated by a regex answering a different question under the same check id - and it is *accepted* at load with its fixtures unrun, because refusing it would report the rule as inexpressible when installing one binary is what it actually needs. **A backend that fails at run time reports `unclear` with no span** (`_finding`'s `message` override): no findings is `clear`, which reads as "the rule was followed". ast-grep reports byte offsets, which are converted to character offsets before anything is cited - slicing the text at a byte offset quotes the wrong code the moment a file holds one non-ASCII character.

The fetch lives in `install_ast_grep.py`, which nothing on the analysis path imports (`tests/test_ast_grep.py` holds that line, along with "no `urllib` in an analysis module"): it prints the URL, the pinned sha512 and the destination, takes only a typed yes or `--yes`, verifies the digest before writing anything, and extracts one named member rather than calling `extractall`. Bump `AST_GREP_VERSION` and every digest together.

**Block states** (`ruleCheck.state`) are listed once, in `check_block`'s docstring. A rule that could not be checked says so and is never rendered as followed.

**The judge tier** (`judge_tier.py`, wired in through `check_block(..., judge=)`; research doc §9.1). On by default since 2026-11-04 - a tier nobody switches on is a tier that does not exist - and `--no-judge` is the offline path, which never imports the module at all. What the default change does **not** touch: no judge answer awards a badge in either direction, and a judge that cannot be reached degrades to the offline report plus a note (`Judge.unavailable_reason`, `build_real_view.judge_mode`), never to a failed bake and never to a different verdict. `build_real_view.make_judge` builds one runner per bake (so the cache and the call budget span every session), `_compute_payload` hangs it on the trace, and `_rule_check_for` hands it to `check_block` - one hop, no signature churn through the pipeline.

`rule_checks.judge_records` splits the parked records two ways. A `hybrid` record goes to `_judge_candidates`: `enumerate_candidates` produces the sites, and each one is a single call carrying the record's statement, its two example lists and that site's text - never the session and never a second rule. Sites past `JUDGE_CANDIDATE_LIMIT`, or left unasked when the call budget ran out, are counted and named in a note, and a record with any unexamined site can never leave its block `clear` (it reads `not-checkable`). A reply that does not parse into the closed set is `unavailable`, never a hard `unclear`. It is not display-capped, because the deterministic half is real: the path, the line and the snippet are facts this tool established, and only the narrow question is asked. Everything else goes to `_judge_semantic` and is **advisory**: the finding carries `advisory: True`, `_state_from` lets it pull a block down to `unclear` but never up to `clear` and never to `violated`, `_apply_rule_check` filters it out before deciding a badge, and its confidence is forced to `low` whatever the record claims. Judge reliability without validity, position bias and self-preference are all documented; an advisory label is what that literature buys.

**The relevance question** (`judge_tier.relevance_request`, `build_real_view.judge_relevance`) is the tier's one contribution to the *wasted-context* goal (§9.1). Delivery, residency, attribution and duplicates stay Python-computed - a judge cannot do them better - and the one thing token accounting cannot say is whether a file that sat there for thirty turns pertained to anything. It shares the runner, the cache and the untrusted-content boundary, and differs in three ways: its closed answer set is `pertinent` / `not-pertinent` / `undecidable` (named on the request as `verdicts` / `unknownVerdict`, because a runner guessing which vocabulary applies would accept an answer to the other question); its cache key is `relevance|<file content hash>|<task digest hash>|<model id>`, the file's hash taken over its path plus its parsed block content, since two files can legitimately parse the same and one cached answer serving both would file a verdict about one file's name under another's; and a file whose summary tries to instruct the auditor has its answer **discarded** and reported `undecidable`, not merely noted. The discard reads `fileInjections`, never `injections`: the digest half is the user's own prompts, and scanning it would let one prompt about prompt injection throw away the answer for every file in the session. Discarding is the only safe direction: the file picked its own answer, so there is no answer left to trust, and `undecidable` costs the file nothing. Files are asked most-expensive-first, because the budget is finite and spending the last call on a file that cost thirty tokens answers nothing anyone was asking.

**Citation or downgrade, and one shared enumeration.** A verdict whose quoted evidence is not in the content the judge was handed cannot be checked by the reader, so `_quote_span` returning None downgrades the finding rather than citing a line that says something else. The candidate sites come from the same `enumerate_candidates` the deterministic tier uses, because a site only one half can see is a finding the other cannot corroborate.

**The cache is what restores reproducibility**, not the model. Every verdict is keyed `(rule_key, question hash, candidate content hash, model id)` - the question (statement plus both example lists) is in the key because one rule section compiles to several records with the same `rule_key` and the same evidence, and without it the second record was served the first one's answer - in a sorted, indented JSON file at `~/.claude/ctxide/judge-cache.json` (`$CTXIDE_JUDGE_CACHE`, or `--judge-cache`), written through after each answer so an interrupted run does not throw away calls the user paid for. A failed call is never cached: a backend that was down must not pin `unclear` onto a candidate for ever.

**Everything the judge reads is untrusted**, so session content reaches a prompt through exactly one helper. `judge_tier.judge_request` takes `(name, text)` pairs and there is no other way in: it clips them, delimits them with a nonce derived from the content itself (a fixed marker is one an attacker can close and reopen; a random one would make the prompt differ between identical runs), emits the instruction and the answer schema *above* them, and scans for attempts to address the judge. An attempt becomes its own `note` finding and changes no verdict. The answer is parsed into a closed set of three verdicts, so a fluent paragraph arguing for a green is not an answer.

A checks file is trusted repo content: its patterns run as written, with no timeout, so review a generated one before committing it - a pathological regex would hang the build.

**Fallback.** A guidelines document (`kind` in global / project / rule) with no checks file falls back to mechanical extraction: a negation cue followed closely by a backticked, code-shaped token, scoped by the globs the block names or, failing that, to known code extensions only, and matched only against written code. Everything it produces is `confidence: "low"` and is reported as **`unclear`, never `violated`** (`_as_candidate`), so the block cannot go red on it: nobody reviewed the pattern, it is a token lifted out of the rule's own prose, and the exception clause two sentences later may permit exactly what it matched. The strongest honest thing the mechanism can say is that it found something worth a human look. Files the agent merely read get no fallback at all: reading a file does not make its prose a rule.

### Conventions specific to this codebase

- The script must stay **stdlib-only**, with exactly one scoped exception: the optional ast-grep binary (see "Rule checks" above) - optional, checksum-pinned, consented, resolved from the tool's own directory and never from PATH, and degrading to `not-checkable` when absent. Anything that does not meet all five of those is a dependency, and there are none. Don't add any.
- **The judge runs by default, and `--no-judge` is the offline path.** Said plainly because the retired version of this rule - "never call an LLM, never make a network request in default mode" - was the kind of guarantee that is worse stale than absent: by default, session content (prompts, the code the run wrote, rule text) is sent to Anthropic's model through the user's own Claude Code CLI auth, and a one-time notice says so on first run per machine (`judge_notice`, recorded in `~/.claude/ctxide/config.json`). Three properties replace it, each with a test in `tests/test_judge_tier.py`: `--no-judge` produces the offline payload and never imports `judge_tier` (the import stays inside `make_judge`); a judge that cannot be reached degrades to exactly the offline report plus a note, with a zero exit code; and no judge answer awards a green or a red badge. Every report names its mode - `judged`, `offline (--no-judge)` or `offline (judge unavailable: <reason>)` - in the page header and as the last line of every `--query` answer, baked as `data.judgeMode` so the two cannot disagree. Rule *interpretation* is still offline: a checks file is authored once, outside the tool, and read as written. The single network call in the repo is in `install_ast_grep.py`, which no analysis module imports.
- All UI changes go inside `HTML_TEMPLATE` - don't split the template into a separate file. Self-contained output is a hard requirement.
- When adding new data to the JSON payload, mirror the existing per-session vs. session-summary split: cheap metadata in `summary`, heavy data in `per_session`. The picker reads summaries; only the active session's full data needs to be "live". Token usage follows this split: `summary.usage` and `per_session.usage` carry the totals dict (`requests`, `inputTokens`, `outputTokens`, `cacheReadTokens`, `cacheCreationTokens`, `cacheCreation1hTokens`, `cacheCreation5mTokens`, `thinkingTokens`, `promptTokens`), each turn payload carries its own `usage` of the same shape, and the per-request `usageSeries` lives in `per_session` only. Attribution follows the same split: `summary.contextTokens` is the one cheap roll-up, `per_session.attribution` (and each turn's) carries the per-file breakdown and the history bucket, and each context file's `cost` / each block's `cost` ride along with the file records. Wasted context follows it too: `per_session.wastedContext` carries the counts plus the ordered `files[]` list, `summary.wastedContext` the same object minus `files`.
- Payload changes are **additive only**: every existing key in `data`, `data.sessions[]`, `data.perSession[]` and each turn record keeps its name, position and value, and new keys are appended. `tests/test_rollup.py::test_payload_is_purely_additive` holds the line against a committed golden payload. This replaces the older "single-turn output is byte-identical to before" invariant, which the drill-down deliberately broke: the payload is the stable contract, the rendered HTML is not.
- Any value the UI shows must be **computed in Python and baked**. `--query` renders only what is already baked, so a rollup invented in JavaScript would put the CLI and the page in disagreement the moment someone asks the CLI the same question.
- Block IDs use `file_slug(path) + "-" + index + "-" + title-slug`, and a context file's own `id` is the `file_slug` half (turn-scoped records prefix both with `turnN-`). Keep both stable across runs - block ids are how the frontend addresses a block and how the deep-link hash names one (`b=`), and file ids are how `--query` addresses a file. The hash's `f=` still carries the display path, which predates the file id.
- Agent rows in the turns list are `.agent-row`, deliberately not `.drill-row`: the drill click handler parses `data-nav`, so a row that navigates nowhere must not match it. Lane occupancy per row is *computed* by walking the baked `turnRows` once (`laneLayout()`), never authored per row - authoring it is what broke tracks across other agents' rows in the prototype. A figure a notification never carried renders as an em dash, never as `0`.
- The `kind`/`scope`/`group` taxonomy on context files drives the file grouping (read / project / global). New file sources should pick an existing kind before inventing a new one.
- The escape pair `.replace("</", "<\\/")` and `.replace("<!--", "\\u003c!--")` in `main` is load-bearing - both sequences would otherwise break out of the `<script>` block. Don't remove.
